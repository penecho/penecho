# PenEcho Agent 集中修改与 Widget 内容自适应升级方案

日期：2026-09-05。状态：分析与建议；未修改产品实现、未启动应用、未部署。依据当前工作区源码、用户提供的请求日志、现有测试及临时故障注入。工作区已有其他改动，本分析未改写这些文件。

## 1. 结论与优先级

建议采用“读取足够的同一版本源码 → 一次多段 unified diff 完成已知修改 → Host 完成有界布局收敛 → 看图验收”的工作流。

现有补丁引擎已经支持这条流程，不需要重写成新的批处理引擎。前段补丁增删行造成后段行号变化，已经有实现和测试处理。应升级的是并发提交边界、Agent 的读取与修改策略、成功回执，以及 Widget 对自然内容高度的支持。

用户补充确认：产品中用户不能直接修改 Widget 源码。此前故障注入人为改变源码与版本，只证明特定模拟状态下的控制流行为，没有证明产品中存在可触发该状态的实际操作路径。因此撤回其作为 P0 风险和升级前置条件的判断；保留为非阻塞的防御性检查候选，也不用于解释历史请求的停顿。

优先级：

1. **P0：处理实际请求中连续截图超时、恢复流程与错误诊断不足的问题。**
2. **P1：保留共享补丁引擎，升级集中修改协议、有界读取与成功回执。**
3. **P2：为适合自然文档流的 Widget 增加有上限的自动高度，并提供溢出诊断。**

异步提交复查属于非阻塞的防御性完善，不作为以上工作的依赖。
4. 每阶段都记录实际轮次与延迟，进行相同任务、相同初始源码的前后对照。

## 2. 现有 patch 的能力与边界

实现依据：[widget-patch.js](../src/server/widget-patch.js#L326)、[最终严格应用](../src/server/widget-patch.js#L480)、[完整结果验证](../src/server/widget-patch.js#L639)。

| 情况 | 当前行为 | 升级取舍 |
| --- | --- | --- |
| 同一次补丁包含多个 hunk，前段增删行 | 各段在同一原始文件上定位，再累计净增删量重算新坐标 | 保留，作为默认集中修改方式 |
| 模型算错 hunk 行数或新文件坐标 | 根据补丁正文重新统计、规范化 | 保留鲁棒性；模型仍输出标准格式 |
| 声明旧行号偏移，但旧侧完整上下文唯一 | 能按上下文找到真实位置 | 保留；行号是定位提示，上下文才是内容依据 |
| 旧侧内容已经改变 | 拒绝，不使用模糊匹配强行应用 | 定向读取冲突区后重新生成补丁 |
| 上下文有多个相同匹配 | 最终严格应用会拒绝 | 扩大上下文；不要只凭行号猜位置 |
| 相邻 hunk 重复未修改上下文 | 能合并完全一致的上下文重叠 | 保留；涉及修改的重叠仍拒绝 |
| 多个虚拟文件中最后一个失败 | 不返回部分结果，不提交前面成功的内容 | 保留整批原子性 |
| 读后 Canvas 版本变化 | 全局 revision 变化不等于目标 Widget 源码变化 | 核对实际变化来源；不要据此假定用户修改源码 |

一个例子：读取版本 R 的文件后，第一段在原第 20 行附近插入 10 行，第二段修改原第 200 行附近的逻辑。第二段的旧侧位置仍以版本 R 的第 200 行为基准；引擎会算出其在新文件中的位置。模型不应把第二段写成基于第一段“执行后”的中间源码。

独立的下一次工具调用则是另一笔提交：它必须基于新的版本。即使底层引擎能够靠唯一上下文搬正旧行号，公开工具也不应因此绕过 `baseRevision` 校验。

当前窄兼容还包括 CRLF 补丁、末尾换行恢复、唯一可定位的一格缩进遗漏修复、严格条件下移除误复制的行号 TAB。最终应用仍是 `fuzzFactor:0`。这些措施值得保留；不能推广成忽略空白、正则替换或“尽量找个像的位置”。

有一个诊断可改进点：前置定位可能利用声明行号选择重复上下文，但最终 `exactContextPatch` 不接受多重匹配，结果仍安全拒绝；此时错误可能退化为泛化 `context-mismatch`，应明确报告 `ambiguous-context`。孤立 CR 换行的兼容也不如 CRLF 完整，属于低优先级边界，不能据此宣称任意换行格式都已支持。

专业惯例上，继续使用模型熟悉的 unified diff、上下文定位、完整验证后原子提交。Git 文档也将重新统计 hunk 行数与整批失败列为既有行为；PenEcho 可以沿用这些语义，不需要实际调用 Git，也不应引入 `--reject` 式部分落地。[Git apply 官方文档](https://git-scm.com/docs/git-apply)

## 3. 非阻塞候选：提交与读取快照的一致性

**纠正：下面的源码修改是 VM 人工注入，不是已确认的用户可执行操作。用户无法直接修改 Widget 源码；在找到实际可达路径前，本节不作为升级阻塞项。**

[canvasAgentReplaceWidget](../src/client/app/canvas-agent-runtime.js#L4154) 当前顺序为：检查 revision、检查空闲状态、生成当前 Widget 快照、等待 hash、检查会话有效、写入。等待 hash 之后只检查会话是否仍有效，没有复查 revision。相比之下，Create 与 Edit 已在异步准备后复查版本。

本轮 VM 故障注入结果：

```text
进入 replace：revision = 7，html = old html
暂停 hash
模拟用户编辑：revision = 8，html = user html
放行原 hash
实际结果：replace 成功，revision = 9，html = new complete html
revision 检查记录：只有 expected 7 / current 7 一次
```

建议把“最后一个 await 结束后，到首次状态写入前”设为明确的提交检查点：

- 再次检查 `baseRevision` 与当前 revision 相同。
- 再次检查会话、取消状态和 Canvas 是否正在由用户编辑。
- 重新获取对象，确认对象身份及相关内容版本未改变；对象被删除、替换或切换 Canvas 时拒绝提交。
- 从这一检查点到同步提交之间不再插入异步工作。若确实需要再次 await，返回后重新验证；不能通过重复异步 hash 无限追逐变化。
- 冲突返回明确错误，不写源码、不追加历史、不更新截图缓存。

同时审计 `canvasAgentRead` 与 `canvasAgentInternalWidget` 的快照组合：源码、资源 hash、整个 Widget hash、revision 应来自同一捕获状态。不能在 await 前取旧源码、await 后拼接新 revision。这个读取边界本轮只进行了源码审查，没有单独做故障注入，实施时须补验证。

按用户进一步明确的产品要求，源码 patch 应从全局 `baseRevision` 解耦：改用目标源码资源的版本或 hash 校验；保留最新几何状态。全局 revision 继续服务 Canvas 同步、历史与几何操作，不再单独构成源码冲突。具体修订见第 9 节；本段取代此前建议保留全局版本作为内容写入门槛的结论。

## 4. P1：把“一口气改完”变成清晰的 Agent 契约

### 4.1 一次读够，不把“读了一次”当成“读全了”

[canvas_read](../src/client/app/canvas-agent-runtime.js#L3861) 默认只返回 200 行。已有总行数、范围、截断状态、资源 hash、版本和 EOF 信息。

完整读取的判据应同时包括 `start=1`、`end=total`、内容未截断。仅 `truncated=false` 不代表从文件开头读过；一个从中间一直读到 EOF 的窗口也可能是 false。局部修改只需覆盖所有计划修改位置及其上下文，不必为形式上的“完整”读取整个大文件。

建议给小文件提供有界完整读取方式，初始预算可设为约 64 KiB、800 行，实际以输出预算为准；大文件返回明确续读位置，或者按相关 CSS、HTML、JS 区域读取。不要简单放大默认窗口，也不要在半行截断后声称整个请求范围已返回。

分段读取必须属于同一版本。若中间用户改了内容，不能把两版文件片段拼成一个补丁基准。

### 4.2 一笔修改用一个标准 patch 字符串

建议将工具说明及 Persona 明确为：

> 阅读覆盖所有计划修改的当前源码。把本次请求已经确定的关联修改组织为一个 unified diff，按原文件顺序排列多个 hunk；所有旧侧上下文来自同一快照。一次提交后查看成功回执，再进行必要的视觉验收。只有具体冲突、读取不完整或新的可见缺陷需要再次读取或修改。

这里的“minimal diff”应解释为少改无关内容，而不是每次只改一个 CSS 属性。相邻且存在修改依赖的代码应合并为一个较大的 hunk，不让后段依赖前段新插入的文本。

保持现有单 `patch:string`；不新增 `patches[]`、逐段执行、模型可见 dry-run 工具或“执行几段再确认”的流程。引擎已经在内部先构造并验证完整结果。

[当前 Persona](../src/server/canvas-agent/runtime.mjs#L168) 还要求约 3,000 tokens / 一分钟后先交付 scaffold，再连续小 patch。建议区分：

- 编辑已有 Widget：默认集中完成已知改动。
- 新建较大 Widget：确有首屏等待或输出预算需求时，才渐进交付可用版本；不要先创建注定马上推翻的骨架。
- 保留来源特定预算、20 次防失控上限，以及完整 Canvas 视觉复核要求。通用 patch 的 256 KiB / 128 hunks 上限不等于 Visual Explorer 可以绕过其 64 KiB / 400 changed lines 的额外约束。

### 4.3 成功回执直接提供下一步所需证据

当前成功回执已有新 revision 和整个 Widget 的 hash，但缺少真实修改范围及更新后局部源码，容易引发“再读一次确认”。建议新增有界信息：

- 本次实际应用后的 revision、Widget hash。
- 每个 hunk 实际落点的旧、新范围，来自规范化后的补丁，而不是原始提交 header。
- 更新后相关源码窗口：上下文各 3 行、邻近窗口合并，建议最多 8 个窗口、120 行、16 KiB；按完整行截断，明确标记省略范围。
- 如果已有布局诊断，则附其结果；没有时不编造成功的视觉结论。

窗口应从本次已验证的候选结果生成，并且只在浏览器成功提交后返回。无需再发一轮模型工具读取。

区分 hash 的作用域：现有 `canvas_read.contentHash` 对应单资源；patch 内部 `current.hash` 及成功 receipt 的 hash 对应整个 Widget 编辑包。不能把两者直接比较。可以通过能力协商增加统一 `snapshot.widgetHash` 与可选 `baseWidgetHash`，继续保留旧字段与必填 `baseRevision`。涉及嵌套 artifact 时，明确父容器版本/hash 与 artifact 资源的归属。

对旧客户端，缺少新能力时按现有安全路径降级。共享 Main Canvas 的补丁调用和返回契约保持兼容，应用范围元数据只按需开启。

### 4.4 根据失败原因决定是否重读

| 反馈 | Agent 下一步 |
| --- | --- |
| 补丁已成功，回执包含相关源码 | 进入视觉验收，不机械重复读全文 |
| header、计数、顺序等格式错误 | 根据明确诊断修正 diff；若证据足够，不读源码 |
| 上下文已变 | 按错误路径与位置定向读取，再生成补丁 |
| 重复上下文、位置不唯一 | 增加足够上下文后重交 |
| revision / Widget hash 冲突 | 获取最新状态，区分用户变化，重建基准 |
| 截图出现新的明确缺陷 | 已有源码足够则直接依据新版本修正；否则只读相关部分 |

截图仍承担视觉验收：补丁原子性证明的是文本按契约替换，不证明视觉正确、JavaScript 正确或需求完整。一次最终截图可能揭示之前无法从源码确定的字体、公式、Grid 或 SVG 问题，不应为了压轮数而忽略。

## 5. P2：固定宽度、内容自适应高度、明确上限

### 5.1 先区分三种裁切

| 情况 | 自动增加外框是否有效 | 应对 |
| --- | --- | --- |
| 正常文档流比 iframe 视口高 | 通常有效 | Host 测量并增长到上限 |
| 内部固定高度、Grid 行约束或 overflow:hidden | 未必有效，可能继续裁切 | 修内部布局，并返回有位置的诊断 |
| SVG viewBox、绝对定位图形或固定比例渲染区裁切 | 通常不能仅靠外框解决 | 调整图形边界或渲染布局 |

提供的工作流包含内部 `height:100%`、`min-height`、Grid 行分配和 SVG viewBox 的修改；不能把这些都归因于 Widget 外框太矮。已检查的轨迹没有外框 `resize_widget` 调用，用户描述的现象在该样本中主要体现为源码内部调整。

### 5.2 推荐交互契约

- 对新建、明确支持自然文档流的说明卡片及普通 HTML，允许启用内容自适应高度。宽度保持由布局或用户决定，高度随内容增减。
- 老 Widget 默认继续使用现有固定尺寸，只有显式启用或源码完成适配后才进入自动模式。固定比例图、动画场景及不支持测量的框架保持原尺寸模式。
- 上限必须是稳定的内容坐标值，不能随 Canvas 当前缩放改变。初始产品参数可试用 `maxContentHeight=2000 CSS px`，同时受画布剩余空间和既有尺寸校验约束；这是待实测调参的建议值，不是当前代码已有规则。
- 达到上限后默认保留内容并内部滚动。这个方案以此为暂定选择；拆成多个 Widget 属于内容结构变化，不自动替用户拆分。
- 用户垂直拖拽尺寸时切换到固定高度，避免松手后被自动布局弹回。横向改变宽度仍可触发自动换行与重新测高；角点拖拽继续遵循现有比例缩放约定。恢复自动高度可放在现有对象操作入口。
- 保持当前位置及其他对象不动；自动增长受 Canvas 边界限制，整页截图检查是否遮挡邻近内容。有相交时报告具体对象，不自动挪动用户已有排版。

周边控件遵循现有 Apple Workbench `context-toolbar` / `tool-panel XS`。首期不增加常驻配置面板。文档内容与 Canvas 宿主工具栏采用各自现有契约。

### 5.3 Host 实现方式

当前 [positionWidget](../src/client/app/canvas-runtime.js#L1617) 将 `w/h` 映射为画布外框，`contentW/contentH` 作为内部视口。仅增加 `h` 会拉伸内容；应同时按现有比例调整 `h` 和 `contentH`，保持文字缩放比。

设本次调整前 `s = h / contentH`，则先把自然内容高度限制到产品上限、Canvas 剩余空间和现有最小尺寸允许的区间，再令 `newH = s × newContentH`。这里不乘 Canvas 的视图缩放 `state.scale`，缩放画布不应触发内容重新定高。

`widget-host` 的内层 iframe 没有 `allow-same-origin`，父页面不能直接读取内层 DOM。应在已注入的可信 bridge 中测量指定内容根节点，通过现有 Host 消息链返回，校验 frame 身份、runtimeVersion、请求/内容代次及数值边界；不要放宽 sandbox。

建议内容根契约：用已有根元素声明自然内容区域，宽度由视口约束，高度来自文档流。不要普遍包一层改变 CSS 选择器，也不要强制覆盖所有旧文档的 height/overflow。外部滚动视口与内部测量根区分开，根元素不以 `100vh` 或外层 `height:100%` 反向决定自身自然高度。

使用 `ResizeObserver` 观察根尺寸变化，并结合现有文档 ready、字体/图片就绪、显式 meaningful update。只对实际活动或当前待捕获的 Widget 工作；合并短时间内重复通知，按版本丢弃过期结果，不做每帧全 DOM 扫描。

不能简单循环执行 `iframe.height = documentElement.scrollHeight`：当内容短于视口时，scrollHeight 可以等于视口高度，无法可靠支持缩短；尺寸写回也可能再次触发观察回调形成循环。需要自然高度根、预期尺寸去重、小幅变化容差、有限收敛次数与超时降级。[MDN scrollHeight](https://developer.mozilla.org/en-US/docs/Web/API/Element/scrollHeight)、[MDN ResizeObserver](https://developer.mozilla.org/en-US/docs/Web/API/ResizeObserver)

只做尺寸调整应复用 iframe，保留输入、选择、滚动与动画状态；源码 patch 本身现有行为会重新初始化内部文档，不能误称修改源码也保持全部运行态。

### 5.4 滚动、截图和事务边界

当前 bridge 使用 `touch-action:none!important` 并向 Canvas 转发手势。启用内部滚动需要和现有交互 owner 协调，不能只加 `overflow:auto`：活动 Widget 的内容滚动、画布平移/缩放、边缘调整和笔输入要有明确优先级，避免单次手势同时滚文档和移动画布。

达到上限的滚动内容，在整页截图中只显示当前视口。工具必须返回“已达上限、仍有可滚动内容”，不能把截图视口等同于全部内容。需要验收隐藏区时按现有捕获预算做指定区域检查；静态图片/PDF导出如要包含全部滚动内容，需要单独定义完整内容导出或分页行为，不能默认已经解决。

建议一次 Agent patch 及其首次有界尺寸收敛，对用户形成一个 Undo 单元。布局可在渲染阶段暂态更新，但历史提交和成功回执必须有明确最终状态：

1. 验证源代码修改并更新内部文档。
2. 在有限时间内等待正确代次的 ready 与内容测量。
3. 校验用户版本和任务状态，完成尺寸收敛及关联历史。
4. 返回 committed revision、最终几何、`settled/capped/unstable/unavailable` 等真实状态。
5. 再捕获完整 Canvas。

超时不让工具永久等待，保留有效内容与有界尺寸，明确报告未收敛。Undo、用户拖拽、取消任务、对象卸载或再次改源码时，应取消旧测量。不能在工具成功返回后，让旧异步回调悄悄改高并使截图、revision 和下一次 patch 基准过期。

长期运行的动态内容变化另按明确的运行态尺寸策略合并处理，不能无限新增 Undo 历史或自动修改保存状态。需在实现阶段明确这类变化是否只影响运行时几何，以及显式保存时如何序列化，不与首次 Agent 提交混成一条隐式链。

### 5.5 有界溢出诊断

建议随 capture 或补丁后的布局回执返回：自然内容尺寸、最终视口、是否到达上限、测量版本、稳定状态，以及少量有证据的裁切候选节点。区分“可滚动内容尚未显示”与“隐藏溢出可能丢失内容”。

内部 Grid、SVG 的几何诊断只能给候选证据，不能把任意 `height:100%` 或 SVG 边界差异直接判成错误。意图仍由模型结合源码和截图判断。不要新增模型每轮必调的独立诊断工具，否则会抵消减少往返的收益。

## 7. 收益估计与验收

用户提供的完整请求持续约 **19 分 58 秒**，有 **20 次工具调用：8 read、6 patch、4 capture、1 skill、1 set_view**。读取包含首次分段与后来的多次接近全文读取；不能将所有读取都算成冗余。

先前固定日志快照显示：首请求输入缓存命中约 87.7%；后一个请求在当时尚未结束的快照中约 85.1%，排除其首个零命中轮后约 98.4%。这些是已有快照统计，不代表后一个请求的最终结果。高缓存命中也不免除每轮重新响应、生成补丁和视觉判断的等待。

可设定的首轮工程目标是该类任务从 **20 次降至 12–14 次工具调用，减少约 30–40%**。这是目标，未做升级 A/B 实测。主要来自少读几次重复全文、合并已知代码修改、避免外框高度试错；现有截图生成记录约为亚秒级，收益主要不在压缩截图文件生成时间。

总时间必须单独衡量。仅作敏感性计算：若真正省掉 6 次“工具往返 + 后续模型续写边界”，每次分别为 10 / 30 / 60 秒，毛节省对应 1 / 3 / 6 分钟，还需扣掉更大的单次补丁、附加回执及测量收敛成本。日志没有足够逐事件时间戳证明其中哪个均值成立，不能把工具轮次降幅直接当成总耗时降幅。

建议先给关键路径补单调时钟时间点：模型请求/首事件/完成，工具收到/派发/浏览器收到/首次结果/完成，源码提交/布局就绪/捕获完成。关联 request、turn、call、revision、cache usage；无需记录额外隐藏推理内容。

前后对照使用相同源快照、相同用户要求、固定模型与 reasoning effort、相近上下文；分别记录冷缓存与热缓存，重复若干次，比较分布而不是单次最好结果。检查总时间、首个可见进展、模型轮次、重复读取字节、patch 次数、失败重试率、首次视觉验收通过率、缓存命中和最终结果质量。

验收底线：

- 插入/删除行后的后续 hunk 正确；含歧义或已变上下文时零误改；最后一段失败时零部分提交。
- hash 等待期间发生用户编辑、删除对象、切换画布时，旧任务不覆盖新状态。
- 小文件一次有界读取即可生成关联多 hunk；成功 patch 不再机械读全文确认。
- 自适应模式既能增长也能缩短，达到上限可访问剩余内容；缩放 Canvas 不改自然高度。
- 手动尺寸操作、输入状态、Undo/Redo、保存恢复、收藏、导出、Web/Desktop/Cloud 的行为符合确定契约。
- 离屏不持续测量；旧代次回调不生效；不稳定内容在有限时间内降级。
- 整页构图及真实内容正确，不能为了数字更好看而省略有必要的视觉检查。

## 9. 用户澄清后的核心修订：内容 patch 与几何、视觉状态解耦

本节取代前文将整个 Widget hash / 全局 baseRevision 作为内容 patch 前置条件的建议。用户没有直接源码编辑入口；拖动、调整尺寸、选择状态和截图是否完成，不应被当成代码已改变。

### 当前实现的四处耦合

1. `canvasAgentReplaceWidget` 首先比较全局 `state.userRevision`。用户确认 Widget 移动/缩放会推进这个版本，即使 HTML 完全没变。
2. `canvasAgentInternalWidget` 对完整 `widgetEditContext` 求 hash。该 context 包含 `box`，还可能包含 runtime/visual diagnostics；这个 hash 不能代表纯源码身份。
3. `canvas_patch_widget` 调用 `assertCanvasLayoutReviewed`；待整页复核的标记可以拦截纯源码 patch。实际请求的回滚后拦截就是这一路，不是 diff 失败。
4. `canvasAgentMutationIdle` 把 `state.widgetEdit` 与正在拖拽的 `state.widgetGesture` 一起当成忙碌；选中后仍处于编辑状态也可能阻塞。松手、选中和未提交的手势历史必须区分。

当前 replace 还把 `x/y/w/h/contentW/contentH` 列入写回字段。因此不能只删校验；必须把提交范围改成实际修改的源码/manifest 字段，保留提交时最新几何，避免把用户移动或缩放撤回。

### 连续 patch 不应强制重读

第一次 patch 以 revision 7 成功提交，会返回 revision 8。第二次使用回执中的 8 即可；重复使用 7 会冲突，但不需要为取得 8 再读取文件。所审查请求中，基于 8 的 patch 成功后，紧接基于 9 的 patch 也成功，中间没有 canvas_read，证明当前系统也不是每次 patch 后必读。

每个 patch 内部本来就有一次 `canvas_internal_widget` 读取，由 Host 在同一工具调用中完成；这与新增一次模型可见的 canvas_read 往返不同。应保留必要的宿主校验，消除多余模型轮次。

### 推荐契约

- 源码资源版本/hash：对应 `widget.html`、`widget.source` 及明确可修改的 manifest。只对本次涉及的资源做一致性校验，明确 Canvas/对象/artifact 身份。快照不包含位置、尺寸、选择、运行时诊断或截图状态。
- 几何状态：`x/y/w/h/contentW/contentH`、层级等保留提交时最新值；内容 patch 默认不写这些字段。改变外框使用明确的几何操作。
- 渲染/视觉状态：截图新鲜度、ready、运行态更新及待复核状态，决定后续视觉验收，不决定源码 patch 能否提交。
- 现有 `contentVersion` 会因 `penecho-widget-updated` 增长，不能直接改名作为源码版本使用。可先使用规范化源码资源 hash，避免急于增加多套持久化计数器。
- 全局 Canvas revision 仍推进，用于同步和 Undo；纯几何变化不再因全局版本不同而拒绝内容 patch。新能力须在工具协议和客户端同时落地，旧客户端按协商能力兼容。
- 当前源码确实发生变化时，例如另一笔已提交 patch 或 Undo 恢复了源码，才按资源 hash/上下文处理真实冲突。若只有几何改变，直接提交并保留几何。
- 当前无实际同对象手势时，选中状态不阻止源码修改。实际手势进行中可由宿主有界等待安全提交点，不让模型为此重读源码或截图解锁。须将几何编辑历史与源码提交历史分开，避免共享 `widgetHistoryBefore` 吞掉用户操作。
- 源码 patch 成功回执返回新的源码资源 hash/版本、真实修改范围和当前几何，供下次 patch 直接续用。
- 移除纯源码 patch 的强制整页截图前置门槛。集中完成关联修改后，再对最新几何和渲染版本验收；截图失败不使下一次源码修复失去资格。新增对象、空间排布继续使用相应布局检查。

### 核心验收例子

读取源码 A、布局 L1 → 用户移动/缩放为 L2 → patch 将 A 改为 B → 结果必须是 B + L2。撤销这笔源码修改后应为 A + L2，而不是恢复到 L1。

读取 A → patch 1 得到 B → 直接使用成功回执提交 patch 2 得到 C；中间不为版本号重复读取。同一大 patch 中的多段修改仍以同一原始源码为基准。

只有截图失败、诊断更新、选择变化、其他对象移动时，源码 patch 应保持可用；最终视觉验收状态必须真实报告，不能因此虚报已验收。
