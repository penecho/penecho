# PenEcho Agent 性能修改计划与收益估计

日期：2026-09-05。状态：实施计划，产品实现尚未修改。本计划汇总前面的源码、请求日志和边界验证结论，取代早期方案中将全局 revision / 完整 Widget hash / 视觉复核作为内容 patch 前置条件的建议。

## 1. 决策

**用户明确的验收目标：这类已有 Widget 的局部源码修改，正常完成时间应在 6 分钟以内，通常只看 1–2 次 Canvas。**此前只预计省 3–9 分钟是沿用过长流程的保守减法，不作为本计划最终目标。

优先处理截图结果消费错误、任务范围与轮次膨胀，再改进两条独立关键路径：

1. **把 Widget 当作有独立源码的文件处理。**内容 patch 校验源码，不因移动、尺寸、选中、运行时诊断、截图状态或其他对象变化失败。成功回执支持连续修改，模型无需为了新版本号再次读取全文。
2. **让截图失败可定位、可恢复，避免超时后叠加渲染和无依据的源码回滚。**视觉验收发生在关联修改完成之后，截图失败不剥夺内容修复能力。

同时改善进展可见性，随后增加适合文档型 Widget 的有上限自动高度。保留现有严格 unified diff、多 hunk、行号偏移修正和整批原子提交，不重写补丁引擎。

不以“用户直接修改 Widget 源码”作为前置风险；产品没有这个操作入口。此前人工注入的源码并发状态仅说明控制流边界，不能成为性能升级的阻塞理由。

## 2. 样本与证据范围

扫描目录 `~/.penecho/logs/requests/`，共 100 份 trace，其中 47 份标记为 `canvas-conversation-turn`。其余包含普通 Canvas 请求；Agent 样本还混有不同模型、不同执行引擎、失败、取消和放弃的请求。统计必须分组，不能用混合平均值承诺加速比例，也不能拿不同任务的耗时作模型速度排名。

重点完整核对的两个最新 Codex native 修改请求：

| 请求 | 模型配置 | 总时间 | 工具调用 | 记录到的工具失败 | 输入缓存命中 |
| --- | --- | --- | --- | --- | --- |
| `1788614468278-de45f8e2-ac81-4b15-97cd-a7690a84073a` | gpt-6-astra / max | 19 分 58 秒 | 20：8 read、6 patch、4 capture、2 其他 | 0 | 87.7% |
| `1788615719487-2c3558f7-94b0-4e6e-9e58-0e1b2d4e0b66` | gpt-6-astra / high | 26 分 58 秒 | 26：8 read、9 patch、6 capture、3 其他 | 6 | 96.1% |

缓存按当前 turn 增量计算；native usage.total 是会话累计，不能直接将最后的累计值当成本次用量。第二个请求本次输入约 409.7 万 tokens，命中约 393.7 万，输出 26,941 tokens，其中 reasoning output 13,330。高缓存命中仍不能消除每一轮响应和生成等待。

第二个请求的 6 次失败为：4 次 `Widget snapshot timed out`、1 次全局版本冲突、1 次视觉复核门禁。9 次 patch 中 7 次成功，另 2 次由版本或门禁拒绝，没有记录到 unified diff 行号/上下文匹配失败。

源码反复读取的范围多有重叠，但中间源码确实经过 patch；不能把每次重叠读取都断言为相同字节的重复读取。可优化的是不必要的确认性读取、取版本号的读取，以及可合并为一笔提交的已知修改。

**日志支持的结论：**没有工具错误的第一个请求也很慢，减少模型往返必须独立于错误修复推进；第二个请求还存在截图失败引起的额外恢复成本。

**日志的限制：**native 的一个外层 step 包含整段多轮工作，events 缺少完整逐事件时间戳，diagnostics 只保留最近 32 条。`rawResponse/completed` 不是浏览器工具的完成时间。现有证据不能把每个间隔准确拆为模型、RPC、主线程或截图耗时。

## 2A. 新发现：截图按 Base64 文本回灌，优先级最高

第一条请求的三个连续 Code Mode 调用：

- 13:27:04 UTC：假设 nested capture 返回 MCP `r.content[]`，失败后执行 `if(!r.content) text(r)`。
- 13:27:17 UTC：仍按相同假设处理，又执行 `text(r)`。
- 13:27:25 UTC：开始判断 `typeof r === "string"`，查找 `data:image/`，提取后调用 `image(...)`。

对应后续输入量从 33,702 → 60,875 → 88,167 tokens，连续两次各增长约 2.7 万。两次 capture 的图片都是 33,908 字节，第二次为缓存命中、复用同一图片；却仍走了完整附件返回和错误文本消费。这是图片 Base64 文本污染上下文的强证据，不是截图图像本身需要这么多自然语言 token。

服务端 `canvas_capture` 的 renderer 本身返回 compact metadata + image attachment，native host 也转换为 inputText + inputImage；问题位于实际 Codex Code Mode nested result 的字符串形态与模型采用的 MCP 解析假设之间。现有 trace 没保存 wrapper 全部最终输出，不能精确把 54,465 个增量 tokens 全都归为 Base64；必须用真实 CLI 形态的端到端测试闭环。

**修改：**明确并验证 Code Mode capture 的唯一消费契约。短期提供准确、固定的解析与 `image(...)` 转发范式，不让模型自行猜 `r.content`、反复截图或 `text(result)`。适配层能提供结构化结果时统一为 metadata 与 image。不要靠新增正则 admission 拒绝来制造另一轮模型错误；优先修返回/消费契约本身。

**验收：**最终送回模型的文本中没有图片 Base64，图像以正确的 image 类型传递；一次正常 capture 不再引发约 2.7 万纯文本 token 增量。同一 cached attachment 不应因 directAttachment fallback 又被重复注入，须检查整个链路而非只检查 renderer 的 image 分支。

既有会话已积累的错误文本，通过原生支持的压缩或正常新会话初始化处理；不直接篡改 provider 历史。相邻用户请求可以保留对话语义，但不应反复携带误注入的图片文本作为必要编辑上下文。

## 2B. 哪些工作应收窄

- 当前 Persona 超过约 3,000 tokens / 一分钟就要求 scaffold、连续小 patch；已有 Widget 修改应退出这条创建流程。
- Visual Explorer contract 无条件注入，且包含“最终再改一个具体全局字体问题”。应改为有真实缺陷才修，不要求凭空制造最后一次修改。
- 约 12 KB 的新建 Visual Explorer 全文应按实际任务加载；普通已有对象编辑只需要短路由与编辑契约。
- native contract loader 既写 durable system section，又在工具结果返回全文。统一成一个权威注入来源，避免显式重复；确认 native 当前轮确实收到全文后才能缩短工具回执。
- 既有科学图的翻译、控制小改，保留原有数学模型。只验证本次影响的变换、旋转、重置及标签，不重新推导全部数学、追加不必要校准面板或重新设计整图。
- 最新请求把英文替换拆成 3 笔 patch，又把交互实现分为多笔，随后继续改说明和字体。局部编辑应把已确定改动整理为 1 笔，确有输出/资源限制时才拆为 2 笔。
- 模型反复生成辅助 diff 组装脚本和截图类型猜测代码也进入输出与上下文。为常用操作提供稳定契约，模型输出标准 unified diff 即可；对必要交互做针对性验证，不反复自造通用 mock 框架。

## 3. 第一批：内容 patch 解耦与减少往返

### 3.1 明确三类状态

| 状态 | 内容 | 对源码 patch 的影响 |
| --- | --- | --- |
| 源码快照 | 目标虚拟文件的实际内容、换行语义及对象身份 | 涉及资源确实改变时才发生内容冲突 |
| 几何状态 | x/y/w/h、contentW/contentH、层级与画布布局 | 使用提交时最新值；内容 patch 不覆盖它 |
| 渲染/视觉状态 | ready、运行时诊断、动画更新、截图新鲜度、待复核标记 | 更新验收状态，不阻塞源码修改 |

全局 Canvas revision 继续服务同步和历史，但不再是纯源码 patch 的前置锁。现有 `contentVersion` 会随 `penecho-widget-updated` 增长，属于渲染失效代次，也不能用作源码版本。

当前完整 `widgetEditContext` 包含 box 和诊断。VM 核验已证明 HTML 不变时，仅 box 或 runtime diagnostics 改变也会改变现有 hash。这是需要消除的误冲突来源。

### 3.2 新提交契约

- `canvas_read` 返回独立的 source snapshot/fingerprint，明确 Canvas、对象和 artifact 身份。对实际涉及的虚拟资源计算精确指纹，排除行号显示元数据、几何及运行时诊断，保持末尾换行语义。
- 一个 `patch:string` 可以包含多个 hunk，所有旧侧上下文基于同一读取快照。仍使用现有引擎定位、规范化和完整结果验证。
- Host 每次内部获取当前对象、验证涉及资源并构造完整候选结果。这发生在同一次工具调用内，不产生额外模型工具轮次。
- Browser 提交仅更新本次涉及资源所映射的字段，并保留 live geometry 和未涉及资源。不能只删除旧版本检查，因为当前 replace 还会写回 x/y/w/h。
- 同一对象只移动或缩放：允许 patch。其他对象改变：允许 patch。目标资源确实变化：按具体路径返回内容冲突。对象已不存在、身份不符或完整结果非法：拒绝。
- 选中状态本身不算忙碌；真实同对象手势与提交冲突时，由 Host 有界协调安全提交点。内容历史与几何历史分开，避免共享 `widgetHistoryBefore` 混入或丢失用户操作。
- 纯源码 patch 不再受 `assertCanvasLayoutReviewed` 阻塞。创建与空间排布保留对应布局检查；Visual Explorer 的内容修复仍遵守资源范围、大小和防失控约束。

### 3.3 读取和成功回执

- 小文件提供有界完整读取；大文件按相关区域读取并明确实际返回范围、截断和续读位置。当前默认 200 行不能等同于完整文件。
- patch 成功返回新源码指纹、实际修改范围及有界修改后源码窗口。窗口合并、完整行截断；初始建议最多 8 个窗口、120 行、16 KiB。
- 第二笔 patch 直接使用第一笔回执。当前 v1 其实也返回新 revision，日志已存在两个连续成功 patch、中间不 read 的实例；无需为获取新版本号强制重读。
- 已有 Widget 默认一次完成所有确定修改。minimal diff 指少改无关内容，不要求把每个 CSS 属性拆成独立调用。
- 大型新建内容确实受输出预算或首屏等待限制时再渐进交付；避免让已有对象修改也机械遵循“scaffold → 许多小补丁”。
- 格式错误按诊断修正；真实源码冲突定向读取；成功后不机械读取全文确认。

### 3.4 兼容方式

通过 hello/ready 的附加能力字段协商 source patch v2，在 native session 工具 schema 固定前完成协商。同一 native thread 中途不切换 schema，resume 校验能力一致性。新旧 client/server 组合按能力降级，不直接提升当前严格相等的全局协议版本。

共享 `widget-patch.js` 只按需增加 applied ranges / resource updates 等详细结果。Main Canvas 旧接口保持兼容。API、legacy CLI 与 Codex native 共用源代码提交语义，各引擎自己的工具包装和流式输出分别验证。

## 4. 第二批：截图稳定性及恢复流程

这批可与第一批并行开发，统一做浏览器集成验收。

### 4.1 先让错误可诊断

当前 Canvas 约 20 秒、outer host 约 18 秒、inner capture 最多约 17.5 秒的多个时限共用 `Widget snapshot timed out`。需要统一 request id，并记录各层明确的 stage、同进程 elapsed、ready/forwarded、runtime generation 和 renderer in-flight 数量。

至少区分：等待 host、等待 inner ready、before hook、呈现帧、加载 renderer、DOM/SVG 渲染、编码、返回及 after hook 恢复。正常记录有界元数据，不依赖仅 remote URL 可启用的调试开关。

### 4.2 避免超时后的渲染叠加

当前超时包装可以先返回，但底层 html2canvas 继续运行；下一次请求可能再开始渲染。这是源码确认的风险，尚不是日志已证实的四次超时根因。

每个 Widget 的真实渲染任务应 single-flight，直到底层任务 settled 才释放所有权。超时后不能仅清掉外层 promise 就允许重入；对仍在排空的任务返回明确状态，并有界等待或失败。过期结果不得覆盖新源码的截图缓存。不能假设 Promise 超时能取消 renderer。

ready 等待与实际渲染分阶段、有独立上限和端到端总上限；请求转发使用真实剩余预算，不在排队后又给完整内层预算。保持活动/离屏状态正确恢复。

### 4.3 Host 负责有限恢复，模型停止盲目修源码

- 可恢复的初始化问题由 Host 执行有限恢复；不让模型不停切换 canvas/object 捕获来重试同一失败。
- 只有截图超时、没有源码损坏证据时，不自动撤回已成功的代码。
- 截图失败后仍允许内容 patch；避免“必须先截图才能修复”的循环。
- 有限重试后返回明确未验收状态。不能把旧版本的成功截图当作最新版本的验收。
- 最终回复区分代码已提交、截图已通过和交互已验证；模拟 DOM 测试不能替代真实 iframe 手势验证。

## 5. 独立小批：进展可见性

当前 Codex native 的 `item/agentMessage/delta` 只累计文本，到 `rawResponse/completed` 才公开。可以在完整公开进展行到达时提前显示，保留现有长度、次数、脱敏和去重规则；普通回答与工具调用 admission 的边界保持原契约，隐藏推理不进入公开输出。

Host 根据实际事件展示读取、提交、等待截图等状态，以及真实已等待时间，不编造百分比或模型已经完成的工作。

这批改善“长时间看起来没反应”，**不计入计算耗时的节省比例**。也不通过增加模型请求生成进度说明。

## 6. 第三批：有上限的自动高度

依赖第一批内容/几何解耦，复用第二批布局就绪与诊断通道。

- 优先支持普通 HTML 和自然文档流的说明型 Widget。旧 Widget 默认 fixed，固定比例图、动画场景和不具备自然高度契约的框架不强制迁移。
- 宽度保持确定，测量自然高度，同时按当前比例改变 h 与 contentH，保持字体缩放；Canvas zoom 不影响自然高度。
- 初始上限可试用 2000 CSS px，受画布剩余空间及既有尺寸约束。这是产品调参起点，不是已验证最优值。
- 到上限默认内部滚动，明确仍有未显示内容。用户手动调高后转 fixed；横向调宽可重新测高。触控滚动与 Canvas 手势要单独验收。
- 测量在可信 inner bridge 中完成，保持现有 sandbox。根节点自然高度、预期尺寸去重、有限收敛、代次取消和离屏停测缺一不可。
- 内部 Grid 固定高度、overflow 裁切及 SVG viewBox 问题返回候选诊断，不能指望增加外框解决全部问题。
- 首次有界尺寸收敛与本次内容提交关联一个明确的 Undo 单元，截图在稳定状态后进行；动态场景长期自动增长另设范围，不无限产生历史或保存动作。
- 保存、恢复、收藏、导出和 Cloud 校验识别 sizing policy。达到上限的滚动内容在静态截图中不会自动完整展示，完整内容导出须明确规则。

## 7. 六分钟的流程预算与收益

默认编辑流程：复用已有初始 Canvas 概览 → 读取一次足够源码 → 一笔多 hunk patch → 一次最终截图 → 回答。通常是 **3 次工具调用**；必要的契约加载或有具体缺陷的一轮修正后，控制在约 **4–6 次**。截图通常 1 次，确有问题再做第 2 次；这是正常路径目标，不是以拒绝工具或交付半成品强制凑数。

| 阶段 | 设计预算 | 约束 |
| --- | --- | --- |
| 获取当前源码及必要上下文 | 0–30 秒 | 小文件一次读够，不重复加载大段无关规范 |
| 理解并生成完整关联修改 | 30–210 秒 | 1 笔 patch 为主，保留原数学与布局，不重做整图 |
| 提交、就绪与首次截图 | 210–240 秒 | 原子提交、正确图像输出、有界截图 |
| 验收，必要时一次定向修正 | 240–330 秒 | 只修明确缺陷；无需修正则提前完成 |
| 汇报及余量 | 330–360 秒 | 如实报告最终状态 |

预算是实现及验收目标，不是日志测出的现有各阶段时间；不在第 360 秒强制停止尚未完成的正确性修复。超出时记录具体原因，继续完成必要工作，并用数据判断目标是否需要按任务复杂度细分。

| 代表样本 | 当前耗时 | 目标 | 达标后的节省 |
| --- | --- | --- | --- |
| 反复读改的复杂修改 | 19:58 | ≤6:00 | 至少约 14 分钟，约 70% |
| 叠加截图错误的修改 | 26:58 | ≤6:00 | 至少约 21 分钟，约 78% |

这些是**达标收益，不是已实现的加速测量**。达标路径依赖：修复图片文本回灌、将 20–26 次调用压缩为 3–6 次、收窄任务契约和生成范围、移除几何/vision误阻塞，以及解决截图恢复。只修 revision 或只让截图快一点，不足以支撑六分钟目标。

最新请求累计输出 26,941 tokens（含 13,330 reasoning tokens）；即使忽略工具 CPU，这也已是一段大规模多轮生成。应记录并压缩不必要生成的来源，不把 reasoning token 全部当作浪费，也不靠降低模型质量、硬截断或换模型制造速度提升。

自适应高度是减少外框试错的后续能力，不是六分钟目标的前置依赖；它也不能解决内部 Grid/SVG 裁切。进展可见性改善等待体验，不计入计算时间节省。

## 8. 验证与发布分批

### 第一批的关键回归

- 读取源码 A、布局 L1 → 用户移到 L2 → patch 得到 B，最终必须 B + L2；撤销源码 patch 后是 A + L2。
- 读取 A → patch 1 得到 B → 用回执提交 patch 2 得到 C，中间没有强制 read 或 screenshot。
- 位置、尺寸、选中、诊断、contentVersion、其他对象 revision 变化，不触发源码冲突。
- 目标资源真实变化、对象删除、资源身份错误、非法完整结果，全部拒绝且零部分写入。

## 11. 本轮落地记录（P0–P1，2026-09-05）

以本节为本轮实际实现范围；前文为分析阶段备选方案，不能视为全部已经交付。

- 提示词：已有 Widget 集中完成已知修改，不按计时拆成 scaffold，不强制再做一次字体调整；成功后用回执继续，只有源码不足、真实冲突或具体缺陷才补读补改。六分钟是软目标，不是终止条件。
- 源码协议：`canvas_read` 和内部读取提供 canonical source package 的 `sourceHash`；纯源码 patch 按该指纹校验，提交时保留实时几何。内容指纹不含 Canvas revision、拖动/缩放、选中或诊断。SHA-256 与浏览器 fallback 指纹都支持。旧客户端仍走原 `baseRevision` 协议，legacy plan / artifact 保持旧契约。
- 连续修改：成功回执提供 `newSourceHash`、`changedResources`、实际 `appliedRanges`、有界 `afterWindows`。沿用现有严格 diff 和唯一上下文匹配，不允许模糊覆盖。读取小文件默认完整返回，显式行窗口仍支持；超预算截断保持完整源码行。
- 历史：选中 Widget 的已有几何修改先单独封存，源码再形成独立 history；成功后不留空 history，下一次拖动重新记录几何基线。
- 图片：native Code Mode 描述提供明确图片/元数据拆分范式；已复用图片不再由 direct attachment fallback 重发，metadata 文本清除图片 data URL。
- 契约上下文：native 首次加载返回全文，同轮重复只返回 identity/hash；非 native 使用既有上下文注入路径，避免重复全文。
- 截图：inner snapshot 和实际 renderer 单一占用，超时后底层未结束时拒绝重入并明确 `render-draining`；ready 耗时扣除后才转发剩余预算；错误携带 host-ready、document-ready、before-hook、renderer-load、DOM/SVG render、encode 等阶段。没有增加超时时长，也不把 timeout 当作可取消 renderer 的证明。
- 进展：native 完整的公开 `Progress:` / `进展：` 行可以提前投影，保持现有两次短进展建议、脱敏和完成时去重；标题请求保留完成后投影路径。隐藏推理不进入该路径。
- Cloud：审核镜像已有改动与本轮前 071 源码一致后，仅通过官方 sync 更新 `app.js`、`widget-host.js` 和对应 provenance；不发布、不部署。

截图真实卡死不会通过无限重试或重载 iframe 恢复：这会破坏交互状态。本轮提供稳定的剩余预算、所有权和阶段错误；仍需使用真实 iframe 验证特定 Widget 的渲染瓶颈。自动高度属于后续 P2，本轮未实施。

收益尚未用固定任务、固定模型进行实施后测量。历史两条请求的 19:58 / 26:58 是基线；降到六分钟意味着分别约 70% / 78% 的达标收益，不能当作本轮已经达到的加速。优先观察重复 read/patch/capture、图片文本回灌、无效 source conflict 和截图重试是否消失，再比较总时间与视觉通过率。
