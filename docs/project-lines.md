# Projects

The Projects page (`/projects.html`) runs work on your computer from a folder of Markdown. The file format is in [visual-markdown.md](visual-markdown.md). Canvas stays as it was: Projects is a separate set of files, joined to Canvas by one bridge module and its entry links.

## Where things are

| Area | Files |
| --- | --- |
| Page | `public/projects.html`, `public/lines/*` (classic scripts, no build step) |
| Server | `src/server/project-lines/`: `format.js` parses and edits Markdown, `store.js` reads and writes the folder, `git.js` runs Git, `agents.js` starts Claude Code, Codex, OpenCode, Pi, dsh and Kimi, `codex-server.js` talks to Codex's app-server, `activity.js` turns what agents do into plain rows, `conversations.js` follows conversations in other apps, `agent-sessions.js` reads what OpenCode, Pi and dsh keep, `kimi-sessions.js` reads what Kimi keeps, `workbuddy-sessions.js` reads what WorkBuddy keeps, `router.js` finds a message's Topic, `canvas-file.js` makes Canvas pictures, `service.js` moves Topics along, `http.js` is the API under `/api/lines/` |
| Canvas | `src/client/app/project-lines-bridge.js`, `public/lines/start.js` (the Start a project panel, shared with the Projects page), `public/project-lines-entry.css`, links in `public/index.html` |
| Tests | `test/project-lines.test.js`, `test/project-lines-page.test.js`, `scripts/verify-project-lines.cjs` (a real browser, real Git, a stand-in agent) |

To run the browser check: `PLAYWRIGHT_PATH=/path/to/playwright node scripts/verify-project-lines.cjs [screenshot-folder]`. It uses installed Chrome.

## Where this is going

You work with whichever agents you like, wherever you like. As long as a folder is linked to a project, what happens there shows up in PenEcho and in its Markdown, and what you ask in PenEcho gets done by your agents. Each agent reads the same Markdown, so any of them can take over. You can look in from PenEcho, your phone or any Markdown viewer, and what you write goes back to them.

Today this works on the computer running PenEcho, and from other devices on the same network. Sync through your own cloud comes later.

People are told this on the Start a project panel (on every empty Canvas and on the Projects page) and behind the help button on Vault and Topic pages. An empty project shows only the agents row, because the New project panel has just said the rest. The panel opens with the agents PenEcho follows, then six pictures with their words, in this order: one vault for all your agents, one Topic that any agent can carry on and hand over cheaply because your requests sit in one short file with the details apart, every branch and agent on one tree, drawing your feedback on a prototype, picture or screenshot, Markdown you can read anywhere, and a memory file for the whole project.

## Followed, not copied

You can talk to your agents in their own apps or in PenEcho. PenEcho watches each agent's own record of the conversation, and what it says and changes comes in by itself, as long as the folder is linked to the project. Nothing is copied across by hand, and nothing needs sending back.

| Agent | How PenEcho runs it | How PenEcho follows it | Where a conversation from PenEcho appears |
| --- | --- | --- | --- |
| Claude Code | `claude -p`, streaming JSON | Its transcript files | Opened once in Claude's desktop app, which then lists it. Topic pages have Open in Claude desktop, through the app's `claude://resume` link, which works while the conversation is running. `claude --desktop --resume` refuses any session a process still holds |

Set `OPENCODE_CLI_PATH`, `PI_CLI_PATH`, `DSH_CLI_PATH`, `KIMI_CLI_PATH`, `OMP_CLI_PATH` or `AGY_CLI_PATH` if PenEcho cannot find one. OpenCode's and Kimi Code's own installer folders, `~/.local/bin` and, for omp, `~/.bun/bin` are looked in as well as `PATH`.

**From an agent's app to PenEcho.** Conversations in a project's code folder, docs folder or any other checkout of the same repository are followed, and only what is said after the project was linked is recorded by itself. **Sync recent conversations** brings in earlier ones when you ask: the button is in the middle of a new project, and in Settings. It takes up to 20 conversations from the last 3 days, latest first, each on its own line with its messages at the times they were said. It wakes no agent, not even to ask where a conversation belongs, and a conversation already on a line is left alone, so syncing again brings nothing twice. What you type goes into the Topic file in your words, as an Ask labelled with where it came from. The agent's steps appear on the Topic page, and when it finishes its turn its last message goes into that work's detail file, with a few words of it in the Topic. Only what a person typed counts: Claude Code's own summary of a long conversation, which it writes into the transcript as if the person had said it, and what PenEcho itself sends an agent, are left out. Work on its own branch shows on the map with that branch. A transcript can go on naming the old branch after a conversation moves to another checkout, so PenEcho asks that folder, and it counts no changes between the two checkouts. Finished work with commits waits for you to merge, and PenEcho never removes a branch it did not make. Vault has a switch to stop following.

- Claude Code's documentation says its transcript format can change with any release. Pi and dsh do not promise theirs either. PenEcho reads only a few plain fields and skips what it does not recognise, so a change would stop new messages appearing rather than break anything.
- Scripted Claude runs and helper agents, including those of OpenCode and dsh, are not treated as conversations. A person running `pi -p` or `dsh --profile headless` by hand looks the same as any other conversation, so it is followed.
- A turn left open with nothing written for five minutes is taken as over, so a conversation closed part way does not stay at work. Claude Code and OpenCode write nothing in the conversation itself while one of its helpers works, so what a helper writes counts for the conversation that started it.
- dsh's files need Node 22.15 or newer to read. On an older Node its conversations simply do not appear. A new conversation in dsh's web app goes to its default workspace unless you pick the linked folder there, and only the linked folder is followed. dsh itself needs Node 24.9 or newer.

**From PenEcho to the agents.** Work is done by the agents themselves, with your own sign-in, your settings and the project's `CLAUDE.md` and `AGENTS.md`. One agent is PenEcho's own and needs nothing installed: **PenEcho**, described under "Run with PenEcho" below. The PenEcho Agent panel inside the Canvas has no part in Lines.

- Nobody is there to answer a permission prompt, so each agent runs with what it needs to work alone. Claude Code runs in its `auto` mode, where its own reviewer approves safe commands and turns down risky ones, with everyday commands also listed for an account or version without `auto` (then it falls back to `acceptEdits` or its manual mode). Codex can write inside the workspace and the folders PenEcho names, and asks your own Codex reviewer for anything else, as its desktop app does. dsh writes inside the same folders and is asked nothing. A saved agent's **Access** in Settings → Agents can open Claude Code, Codex or dsh up to **Full access**: Claude's `bypassPermissions`, Codex's `danger-full-access` with approval `never`, dsh's `danger-full-access` preset. The agents below already run every tool, so their Access shows Full access with no choice; PenEcho's own agent keeps to its folders and command list. Kimi with `--prompt` approves its own tool calls, with the docs folder added to its workspace. OpenCode runs with `--auto`, which approves anything your settings do not deny. Pi has no permission prompts of its own. omp does, so it runs with `--auto-approve`, its yolo tier; any rule your omp settings name still applies. Antigravity's headless mode quietly turns down any tool that needs approval and carries on, so agy runs with `--dangerously-skip-permissions`, with the docs folder added through `--add-dir`.
- **Run with PenEcho.** The built-in agent is one more entry in `ADAPTERS` (`agents.js`), last in the list so an agent you installed stays the first choice. It is here once this computer is signed in to PenEcho Cloud, whose models are paid with credits, or has an API connection of your own in the Canvas's settings (`connections.json`); with neither, Agent setup shows it as Not set up with a Sign in button. PenEcho starts `src/server/project-lines/penecho-runner.mjs` with Node: the dsh loop (the same one the Canvas engine runs, mounted from `src/server/agent-core/loop.mjs`) with four tools. `read`, `write` and `edit` (`@deepseek-ai/dsh-tool-fs`) work only inside the run's working folder, the docs folder and any folder a merge adds; a path or a link that leads anywhere else is refused, and a file must be read before it is changed. `bash` runs one foreground command if every part of it starts with a program on the list unattended Claude runs get (`src/server/agent-core/run-commands.js`, the one list both use) or is the project's memory command; variables set in front, command substitution, here-documents, `&`, and a redirect or `mkdir`/`touch`/`mv`/`cp`/`sed -i` that would write outside those folders are refused, with the reason given to the model. As for any agent, a program on the list such as `node` or `git` is not itself confined. It prints the JSON lines Claude Code prints and reads its words the same way (`input:"stream-json"`), so the thread, words added while it works and Stop need nothing of their own; Stop also ends the command it was running. It gets the same Ask and instructions as every agent, so pictures go through the file-drop under "Pictures". A conversation is carried on by a new process: what was said and done is kept in `project-lines/penecho-sessions/<id>.json` with the instructions it began with, and given to the next run as a recap (bounded, newest kept), not as the full history.
- **The runner holds no key.** A model proxy in the server (`src/server/agent-core/model-proxy.js`) listens on `127.0.0.1` only. Each run gets a secret of its own in its environment (`PENECHO_MODEL_PROXY_URL`, `PENECHO_MODEL_PROXY_SECRET`); the proxy knows the run by it, adds the Cloud account token (`prepareHostedConnection` in `cloud-connector.js`) or your API key, and passes on only the two model calls (`/chat/completions`, `/v1/messages`), so the account's other addresses cannot be reached through it. The secret is forgotten when the run ends. What the runner is told about the model (`GET …/profile`) holds no key and no address but the proxy's. PenEcho's own environment can hold the first AI connection's key (`AI_API_KEY`, `OPENAI_API_KEY`); the adapter blanks every variable named like a key for the runner, the runner drops them and its own secret from its environment at start, and a command it runs sees only a short list (`PATH`, `HOME`, the locale, `SSH_AUTH_SOCK`, `PENECHO_DOCS_FOLDER`). Which model: a name picked on Agent setup, where the list is Cloud's models by name and then the models of your own connections; nothing picked is Cloud's first model when signed in, otherwise your first API connection; a typed name PenEcho does not know is asked of your own connection. Check with `node --test test/project-line-penecho-runner.test.js`: a run against a stand-in model writes inside its folders, is refused outside them, is read by the thread's own parser, and shows no key to a command.
- Codex runs through its app-server, so its threads are the same kind Codex's desktop app lists. A Codex project lists threads by folder, so a thread appears under a project only if the folder it ran in is one of that project's folders. PenEcho runs in the project's docs folder or in a worktree under `~/.penecho`, and does not edit Codex's project list.
- Claude's desktop app leaves `claude -p` sessions out of its list, but Claude Code can open one there with `claude --desktop --resume`. **Open in Claude desktop** on the line does that when you ask, and the app lists it from then on. A run that finishes never opens the app by itself, so it does not take you away from what you are doing. It needs macOS and a Claude subscription sign-in.
- Some agents exit normally even after giving up on every retry. What the agent said last counts too, so that still stops the Topic with the reason.

Saying more in PenEcho goes to the same conversation, wherever it began. If that conversation is busy in the other app, your message waits until its turn ends. dsh refuses to resume a conversation that runs under one of its agent presets, which is every conversation started in its web app, or one open in its web app right now. There, a new conversation carries on from the files, and what was said in the other one stays in the Topic.

## Which Topic a message belongs to

The home's box always starts a new line, and says so. To add to a line, open it and write in its box, which says it adds to this line. Nothing is guessed there.

Two agents can share a line. Each conversation keeps its own Work: what it says and does goes there, its reply becomes that Work's result, and its going quiet ends only that Work. Both show as running together, and the line finishes when the last one has. PenEcho starts nothing by itself meanwhile.

A new conversation in another app is a new line. It joins an existing line only when its first message was pasted from one of that line's Asks: Paste with context names the Topic's file, and the words of an Ask marked Not sent find it even when pasted without context. Nothing else moves it, not even naming a Topic's id, and no agent is asked where it belongs. The rest of that conversation stays on the same line. This holds across projects: an Ask pasted into an agent open on another project's folder still goes to its own line. The folder's project keeps reading that conversation and hands it on. Pasted without context, the words find another project's Ask only for a new conversation, and an Ask waiting in the folder's own project comes first. A line off main, or one whose agent is in another project's checkout, takes no branch from that conversation.

## What happens when you send a request

A request is one run of one agent, the same as typing it into that agent yourself.

A Line called by the first words of its Ask is still unnamed. Its first agent chooses a short name itself; once an LLM or the person has named it, later Asks, agent switches and restarts keep that name and ask for no new one. This includes names supplied in replies from another app. The person can still change it with Rename.

1. PenEcho finds its Topic, or saves your words as a new `lines/x.md`. In a project with code it makes a Git worktree on a new branch, `penecho/x`, so your checkout is untouched.
2. It starts the agent in that folder, with your words and a few lines saying where things are. Claude Code runs as `claude -p --output-format stream-json`, with file edits and everyday commands approved. Codex runs through `codex app-server` in its `workspace-write` sandbox, or `codex exec --json` for a version without one.
3. The agent does the job its own way, including any testing and checking. What it prints appears on the Topic page as it happens: what it says, each file it reads or edits, each command with its output.
4. When it finishes, PenEcho commits anything left uncommitted, writes its last message whole into `works/x/work-1.md`, with what it changed and what it did, and adds a few words and a link to the Topic. Changed code stays on its branch, marked Finished, and nothing merges. A request that changed no code, such as a question, simply finishes, and its empty branch is removed.
5. Anything you say next, in the page or in any editor, becomes the next Ask in the file, with its own Work after it, and goes back to the same agent in the same conversation (`--resume`, `codex exec resume`). If it arrives while the agent is working, it waits and goes in as soon as that run ends. If you chose a different agent for it, the one working is not stopped: it finishes its own Work, and then the agent you chose does yours in a Work of its own. If the agent's own history is gone, a new conversation carries on from the files.

If the agent exits with an error, the Topic stops with the reason at once. Retry carries on in the same conversation. PenEcho never retries by itself, so nothing runs twice without you asking.

**Stop** sits beside Pause and Resume in a line's head while it has work still to do. It ends that work for good: the run is stopped, and each Work not finished yet gets `· stopped` in its heading, ticked, and shows greyed out. **Discard**, in the panel of a Work that stopped with an error, does the same with `· discarded`. Either way the Work counts for nothing: not working, stopped, to review or finished, on the line's counts or the home's. The line goes back to where it stood without it: finished if its branch has changes, done if not, paused if other work is still to do. Nothing is merged and no branch is removed. Carrying the conversation on in the agent's app brings the Work back.

**Send again** sits under the latest Work when it stopped with an error, was stopped or was discarded, and nothing runs on the line. The Work goes to the trash, as Remove sends it, with its detail file (Deleted brings it back). Its Asks turn `· Not sent` again where they were. Run with or Paste then picks who does it this time, Edit changes the words first, and nothing runs until you choose (`POST …/topics/<slug>/resend {step}`).

An Ask sent after a Work that ran and stopped, by Run with, by Retry or by writing it in the Markdown, goes under that Work and gets a new Work of its own, which carries on the same conversation. The stopped Work stays above it, greyed out as Stopped, with `· ended` in its heading and why it stopped in its detail. A Work that stopped before it started is the one that runs. The page moves a card when its place in the Markdown changes, so a sent Ask leaves the end of the line for its place there.

A background run has nobody to answer a permission prompt. Whatever your agent would have asked about is decided by its own reviewer (Claude Code's auto mode, your Codex reviewer) or simply not allowed, and it says so in its summary. dsh's sandbox, for example, refuses to open local ports, so a test suite that needs one cannot run there. PenEcho widens a sandbox only when a saved agent's Access is Full access. Every Work is also told to check pages in a headless browser, never in your own Chrome, and Claude Code to run one plain command per call.

Every three seconds PenEcho compares each Topic's Asks with what it last handled. This only runs while PenEcho is running. An agent PenEcho started goes with it when it quits. When PenEcho starts again, it first reads what each agent wrote meanwhile: one that is still going, or finished, is simply followed. Work whose agent went with PenEcho then carries on by itself, in the same conversation, told that PenEcho restarted and to check the files for what it already did. Its Work keeps running, and its history says PenEcho restarted instead of showing an error. It stays stopped, with Retry, when "Agents wake when a Topic changes" is off, when its old process is somehow still running, or when it has already carried on three times in a row, each lost within two minutes.

## The only times it stops to talk to you

- **`/grill-me`**, or saying "grill me": the agent asks one question at a time. Your answers go back to the same conversation until you press Go ahead.
- **`/prototype`**, or a message that opens by asking for one, when it runs in the background: the agent makes one self-contained HTML page and waits. You approve it, or say what should change. The word somewhere in a message is not asking for one.
- **A decision only you can make**: the agent adds it under "Questions for you" in the Topic file. Tick an answer anywhere.

An agent can also stop on a question in its own app: `AskUserQuestion` in Claude, `ask_user_question` in dsh, `question` in OpenCode. It is waiting for you, not working, so the line says **Answer**, in amber, in the place Unread goes, and leaves Now. Its stop, Work box and panel say the question in the agent's words, and the choices are words too, because you pick them in that app. **Answer in Claude** opens the conversation. Where no click can open it, the button copies the command, as with dsh. It stays until the answer arrives, however long you take, so opening the line does not clear it. The Work does not finish in the meantime. A conversation closed without answering stops counting after a day. The Topic's own status block still says Working, because the file is not rewritten for this.

A `/grill-me` stop and "Questions for you" say Answer too, and so does a reply ending in a question when your last Ask said grill me. Any other reply ending in a question stays on Needs you with Reply, because "Want me to…?" has stopped nothing. There is no popup, sound or system notification.

Topics written the older way, with a second `x.tasks.md` file, become one file the next time PenEcho looks at the folder. The old files stay in `.history/`. See [Visual Markdown](visual-markdown.md).

## PenEcho Lines

The app opens on PenEcho Lines, every time: the empty Canvas shows recent projects, a picture of how a project, its lines and their files belong together, the six things a project gives you, and **Start New Project**, which goes to the New project page. A Canvas kept from last time waits underneath, covered completely (`pls-kept`); **Back to my Canvas** puts the panel away. On an empty Canvas or a kept one, a stroke can start anywhere off the panel's buttons and links (`window.projectLinesWelcomeOpen` in the bridge, read by `studio-navigator.js`): over a kept Canvas the cover lifts as the stroke starts, the stroke lands on that Canvas, and the Hand a kept Canvas opens with turns into the pen. Scrolling over the cover does not move the Canvas under it. Opened from a project to draw, the Canvas never shows it. **New canvas** on the Canvas page puts it away too: the new Canvas opens on the Canvas's own welcome and examples (`window.projectLinesNewCanvas`, called from `openNewCanvasDialog`).

**New project** (`projects.html#new`, `newProjectHTML` in `pages.js`) is a page: the six things a project gives you, then the form beside the example projects. The agents found here are in Agent setup, and the drawing skill is offered on the new project's home. DeepSeek Harness counts as found from its own app (`dshInApp` in `agents.js`) when no `dsh` is on the PATH. It is drawn when you come to it and not again while it is on screen, so a half-typed name stays put as the open project changes.

**A line** holds four kinds of node: a note and a drawing (`## Note`, `## Canvas`, yours, read by no agent), an Ask, and what an agent hands back (a Work). The box has two ways out, **Save as note** and **Send to AI**, and Enter takes the filled one: Save as note on a line with nothing to do with code, Send to AI on a code line. An idea under an empty project's box can choose for it (`flags.prefer`). Notes are edited in place (`edit-note`), notes and drawings removed with `drop-yours`; Asks that reached an agent cannot be edited. Asks and notes are shown as Markdown with LaTeX (`wordsMd`, `texPrep` and MathJax, loaded the first time a formula is on screen, in `markdown.js`).

**Lines off main.** A project with a code folder can have lines that are not about the code: the box's branch menu and the map's Off main label both start one (`offMain`, front matter `git: no`). A line made before the project had a code folder names no code folder and no branch, so it stays off main when a code folder is linked later: main is what was made for the code folder (`offMainDoc`). On the home they are listed apart, below the whole of main: an Off main head (open count, New line, Start with a drawing) and a card of their own, with their own days and clocks and a dashed trunk. They have no branch, no merge, and work in the docs folder. A new line sent or saved with Off main chosen stands there from the first moment.

**The map's order.** Lines go by the time they started, or **My order**: drag a line by the grip before its name, among the lines beside it, and the map keeps that order (`lineOrder` and `lineSort` on the project). **By time** goes back.

**An empty project** has the Canvas and the box side by side. The Canvas is only a door: **Open the Canvas** opens the real one, and what you draw comes back as a new line's first node (`asLine` in `openDrawing`); nothing is drawn on the page. The box is beside it, with two things to ask for first under it. Then Sync when there is a code folder, links to the example projects (below), what a line holds, and the agents PenEcho follows. With no code folder, the folder row says what linking one does: the latest conversations from every agent in that folder sync here. Settings says the same.

**The sidebar** shows each project's newest Lines by creation date. A Line keeps its place when it is opened or receives more work. Five Lines show initially, along with the current Line if it is older. **N more** shows the rest. This browser keeps that project’s list expanded across updates, navigation and reloads until you click **Show fewer**. Folding and reopening its folder restores the chosen list length. Drag a Line within its list to move it, hold then drag on touch, or focus it and press Alt+Shift+Up or Down. This browser remembers its position separately from its recorded dates. Hover a Line and open **…** for **Pin** or **Unpin**, **Archive**, **Mark reviewed**, and **Delete**. The dots are also available on keyboard focus and on touch. Eligible pins from all projects appear once under **Pinned**. Reviewed, archived and deleted Lines leave both lists. A spinner or colored dot shows the Line’s current status. The folder button folds a project, and the browser remembers that choice. A Line in another project opens directly on that Line. **Back** and **Forward** at the start of the bar, and Command or Control with `[` and `]`, go through the pages you have been on, across projects (`history.js`).

**Each part of the map** (the project's name or main, and Off main) has **New line** and **Start with a drawing**, which opens the Canvas and makes what you draw a new line's first node there. Main of a code project also has **Sync conversations**: the latest 20 conversations in the project's folders, however old, each becomes a line. A project created with a code folder does this by itself right after Create; each line shows as soon as it is read, and if nothing comes in, the empty project page stays.

**The project card** sits on the home's right side, under Recent: the project's name, its docs and code folders (a click opens one in Finder on the computer running PenEcho, or copies its path from another device), when it started, how many lines it has and how many are archived, and **Rename** and **Archive**. Rename changes only the name PenEcho shows; the folders keep theirs.

**Archive a project** from its card or its Settings. It leaves the sidebar and the Canvas home, its folders and lines stay as they are, and the toast offers Undo. **Archived**, just above New project at the foot of the sidebar, appears once something is archived and opens a page of its own (`projects.html#archived`) listing archived projects, newest first, with the day each was archived (`archivedAt`), **Restore** and a bin that deletes the project for good. Check with `scripts/verify-project-line-info.cjs`.

**Agents**, a page of its own above Providers and Settings at the foot of the sidebar, is the same for every project, since agents belong to the computer (`projects.html#agents`, with the saved agents and the agents on this computer; the same page also holds Canvas AI (`#agents/canvas`: model, thinking effort, automatic responses, AI drawing and suggestion spending) and MCP (`#agents/apps`: MCP status and desktop setup). Its three cards switch sections directly. Ordinary Canvas view preferences and General remain in Settings. Problems come first: not signed in, a `*_CLI_PATH` naming no file (a bare name, as the Canvas connection writes, is looked up like any command), a command that does not start (with what it said), or installed where PenEcho does not look, found in common folders or by the login shell. Tips, such as an app too old to open conversations, are not counted. Agents not installed are listed last with **Copy install prompt**. It goes to runs as `--effort` for Claude Code, the turn's effort for Codex's app-server and `-c model_reasoning_effort=…` for `codex exec`, `--variant` for OpenCode, `--thinking` for Pi and omp and `KIMI_MODEL_THINKING_EFFORT` for Kimi Code. Only a level the model in use takes can be picked, and picking a model that does not take the picked level goes back to the agent's own level. dsh shows "its default" with no box: its headless mode takes no model (read in its own help, 0.2.2), so there is none PenEcho could run it with. **Change** says where to change the agent's own setting, and that asks pasted into the agent's app use the model picked in that app. One agent gets an extra check, from runs that failed while the agent's own app worked: dsh with no DeepSeek key in `DEEPSEEK_API_KEY`, `~/.dsh/.credentials.yaml` or `~/.dsh/.env` (its headless mode reads no other store). It is a problem with a fix prompt. **Try a run** on each installed agent runs one short real Ask ("Reply with just the word OK") the way PenEcho runs Asks, in an empty temporary folder, with a two-minute limit (`POST /api/lines/agents/try/<id>`, this computer only). It costs a few tokens, so it runs only when clicked. An answer shows **Answered**. A failure becomes a problem titled "A test run failed", with what the agent said (an error from its JSON lines, the last line of stderr, or the model address it was waiting on), and a fix prompt that holds the exact command and the settings PenEcho added. **Check again** clears earlier test runs. The sidebar shows how many problems there are, the check is kept two minutes, and **Check again** asks afresh and refreshes the agents everywhere. Only the computer running PenEcho sees it. Check with `node --test test/project-line-agent-check.test.js test/project-line-agent-models.test.js test/project-line-penecho-runner.test.js` and `scripts/verify-project-line-setup.cjs`.

What you can do with a note, a drawing or an Ask (Edit, Copy, Refer, Remove) is in a small toolbar at the card's top right, shown on hover or keyboard focus (`nodeTools`). A Work's line shows the agent's round logo. Removing a note or a drawing asks nothing: the toast offers **Undo**, and the removed node is kept in `.trash/removed/` in the docs folder, so the line's ⋯ menu lists it under **Bring back** until it is restored (`drop-yours` returns its id, `restore-yours` puts it back after the node that was before it). **New canvas**, a dashed row after the last node, opens the real Canvas; what you draw comes back as a Canvas node at the end of the line (`toLine` in `openDrawing`). The panel on the right takes three quarters of the width it used to.

**The box's keys.** Enter takes the first button, and Command+Enter (Ctrl+Enter on Windows) the other; each button shows its key.

**Paste with context** copies, and opens an agent's app only when an agent has already worked in this project: the line's own conversation, else the latest Work on the line, else on the line updated last (`lastWorker`). Before that it stays a copy.

**Delete** is at the end of a line's ⋯ menu, on the map and on the line page. The line's file moves to `.trash` in the docs folder; code and branches are not touched. The toast offers Undo.

**Archive and Deleted** are always in a project's bar. Archive holds the lines you archived (Back to lines). Deleted holds deleted lines and the notes and drawings taken off a line for 7 days, each with Restore; after 7 days they are gone for good (`purgeDeleted`, `KEEP_DELETED_MS`). A line's files folder is never deleted with it. A note taken off a deleted line comes back once its line does.

**Pictures in a note or an agent's reply** are shown large and first, as a drawing on its own is: the picture, its name and Edit on canvas, then the words (`bigPic` in `line.js`).

## A Topic's page

Any click on a line on the home, whichever stop or wherever on it, leads to one page: the line swings across to the side, and the rest of the page comes up around it. An archived Topic in the home's list opens the same page. Going back, it drops to its row again.

- **Down the left**, the project sidebar stays visible, followed by the line, with a stop for every Ask and every piece of work, each in words. **Hide projects / Show projects** in the head remembers your choice on line pages in this browser; returning home always shows projects again. Your pictures show small beside your words. The line folds to dots, which say the same when you point at them, and in a narrow reading area it opens from the head. Clicking a stop goes to that place in the file. As you read down the file, the line shows where you are.
- **In the middle**, the Topic's one Markdown file, in order: your words as they are, and each piece of work as a box with a few words about it and its pictures. Every picture says **Click to preview** and opens in a lightbox. A picture with a Canvas file also has a full-width **Edit on canvas** button. The box at the bottom carries on with this Topic and its agent, and either can be changed.
- **On the right**, whichever piece of work you open, or the latest one by itself when there is room: its pictures and words together, shown as a page to read, with Source one click away. Formulas in results and activity replies use the same local MathJax renderer as notes: `$…$`, `\(…\)`, `$$…$$`, `\[…\]` and equation/align blocks, including pasted LaTeX documents. Reading typesets them automatically; Source and Copy keep the original TeX. Code examples remain literal, and an unfinished display formula stays readable until its closing delimiter arrives. Documents it changed open as pages too, before anything is merged. Details opens what it did and what it changed. Under that, always in view on two lines, with a result or without one: the way to that Work's own conversation and its file, then the folder and the branch. The panel's head says which agent. On a narrow screen this opens over the page. Check the math renderer with `node --test test/project-line-math.test.js`.

The file's name at the top opens the file itself, to read, edit or download. Because the words are saved in ordinary Markdown, you can read all of this from a phone or any other Markdown viewer.

## The home

A project's home answers three questions: what needs you, what is happening, and what was decided. It is worked out from what is in the folder, so a project has no type to choose.

| The folder holds | The home leads with | What the box does |
|---|---|---|
| Code, or Topics in progress | The map | Starts or joins a Topic |
| A Topic asking for slides, or a slide file, and no code | The slides, their sources and outline | A file sent on its own becomes a source |
| Only pictures | The pictures | Starts a Topic |
| Only notes | The notes | Plain words become a note, unless they ask for something to be made |

- **Now** is at the top of the page: each running Topic, what its agent is doing, its last actions and which app has the conversation.
- **Needs you** is one line under it: one question, stopped Topic, Ask not sent yet or something to review at a time, saying which of how many, with its button. Pressing **Reply** takes that hint away on this browser, and a different question from the same line brings it back. Every message there, and every warning under it, has a **×** that closes it on this browser and shows the next one; something new from that line shows again, and so does **Retry** on it. A branch with something to merge says so on its own label, and each finished line offers **Merge**. Archived lines are never on it.
- **The counts over the map are its filters**: working, stopped, to review, finished and unread. Pressing one shows only those lines, in its own colour's soft fill, and pressing it again shows them all. The counts stay those of the whole project, the one that is on stays shown at 0, and a line started while a filter is on shows beside the ones it picks (even after a trip to the new line's page) and the filter stays on, until a count is pressed again. `MAP_FILTERS` in `panorama.js`; the filter is kept per project until the page reloads.
- **Nothing is repeated under the map.** A project with lines ends there, and its pictures, notes and files are one click away in the Vault. A project with no lines at all shows that grid in the map's place, because it has no map, and the box in front of it is how you add to it.
- **The box is where you start anything.** Typing `/` opens the quick starts, and `/topic` asks which template to begin a Topic from: Blank, Development, Meeting, or Study and research, which write their headings in. No button sits on the page for it.
- **Recent** is all that is on the right. It comes from each Topic's status and when its file last changed, so there is no separate log to fall out of step. A Topic always opens on its own page.
- The sidebar lists pinned projects and the six most recent, and keeps the project you are in. Anything else is one search away. Drag a project's name (or its icon in the compact sidebar; hold first on touch) to reorder it within its pinned or recent group, or focus it and press Alt+Shift+Up/Down. The order is remembered in this browser, shared with its other tabs and the Canvas sidebar. Recency still selects the six recent projects. Clicking or tapping still opens the project; swiping before the hold scrolls as usual. Cross-group drops never change pins, and Escape or cancelling a drag leaves the order alone.

Switching projects resumes each project's last screen, including its selected line and Work. This browser remembers those routes through reloads; explicit links and browser Back/Forward take precedence. Switching away and back also retains the line's reading positions and a deliberately closed Work panel during this visit. Drafts on same-named lines belong to their own projects, including their attachments. Clicking the current project's row still returns home. A missing Work falls back to its line; a missing line or document falls back home. Narrow windows keep projects as an icon rail, and line/work overlays stay inside the reading area so projects remain clickable. Check with `test/project-line-navigation.test.js` and `scripts/verify-project-line-navigation.cjs`.

On the map a request reads Ask, Work 1, Finished, and each thing you say next adds an Ask and a Work. Finished is not a step and is not written in the file: it is where the work stands. It says **To review**, in amber, until you have marked every finished Work **Reviewed**, and clicking it opens the first Work still waiting. Merging from there stays your choice, reviewed or not. A finished line stays on the home until you press **Archive**.

## Sending an Ask

PenEcho does not type into a conversation that is open in another app. `claude -p --resume <id>` writes a separate branch into the same transcript, so the conversation open in the app never sees it, and it runs with fewer tools. So your words go in the Topic first, and you hand them over yourself:

1. You write in the box and send it, with the one button there is. The Ask goes in the Topic's Markdown straight away, marked `Not sent` in its heading, and its pictures go in the Topic's folder. A new request opens its new line. In a Topic, it is the next Ask there. Nothing is copied yet.
2. The Ask is amber and says it has not been sent, with **Run with X** (below) and two Paste buttons. **Paste with context** copies your words, the full path of each picture and the path of this line's Markdown file. **Paste without context** copies your words and pictures alone, and you go to the agent and conversation you want. After copying, **Paste with context** goes on to the agent's app when PenEcho is sure of the place: this agent's conversation on this line, or a new conversation in the line's folder if it has none here. An arrow on the button says it will. If it is not sure, it stays a copy and nothing opens. When PenEcho can run an agent, Run with is the filled button. Otherwise the Paste that fits is: without context once the line has a conversation, with context before that. The Ask says what the context is: only this one file, with the original Asks and a short note on each Work, about a tenth of the size of the Work detail files, which are not passed. A request to draw also points at the README's "For agents", which says how to reach the Canvas. Your words come first, then the pictures' paths, then what PenEcho adds for the agent (the folder and branch to work in, this file, how to search earlier Asks), in one `<penecho-context>` block at the end. So the agent sees where your words stop, the app names the conversation by your words, and no line of `=` or `-` turns your last line into a heading. PenEcho drops the block when it reads the message back from the transcript, and still reads messages pasted before the block existed.
3. You paste, change anything you like, and press Send. Words and attachments always take two pastes, because no app keeps both from one. Claude's box and OpenCode's keep only the picture and cancel the words, and Codex's keeps only the words. Read from each installed app's code, and seen in real use in Claude: a paste with a picture lost the words.

   So a **Copy the picture** or **Copy 2 files** button follows the words: press it and paste again, and they are attachments in the agent's box. The paths stay in the words, so an agent still reads the files if you skip this step or use a terminal. The second paste is macOS only, on the computer running PenEcho.
4. PenEcho reads that message from the agent's transcript. If it is the same Ask, word for word, with one of its pictures, or with most of its words, the Ask becomes that message, in the words really sent. Otherwise it is a new Ask, and the one marked `Not sent` stays until you send it or remove it, on the page or by deleting it from the Markdown.

For a picture of an Ask not sent yet, **Edit on canvas** opens the Canvas and what you draw replaces it in that Ask. Once an Ask has gone to an agent, what you draw on its picture waits in the box instead. Clicking either picture itself only opens its preview. None of those buttons are in the Markdown. An Ask marked `Not sent` wakes no agent, is not told to the next piece of work, and stays at the end of the line.

**Edit** on an Ask not sent yet moves it back to the box: it leaves the line, and its words, attachments and quotes are in the box to change and send again. Its attachments wait in `files/_incoming`, like any new one, so they do not read as something the line's work made. On a line holding nothing else, the line goes too, its file to the docs folder's `.trash`, and the words go to the home's box, where sending starts a line again.

**Reviewed** on a finished Work is one click, on its box or in the right panel, and it does not open the Work. The box keeps its place and its whole result, pictures and all: a green edge down its side and the checked mark are the only change, and the count at the head of the line goes up. Click again to undo. It is one line at the top of the Work's own detail file (`reviewed: 2026-11-07 04:20` in `works/<slug>/work-2.md`), so the Topic stays exactly as it was and the line doesn't read as Unread. A Work that opens again, because its conversation carried on, loses it: there is something new to review. The line says To review until every finished Work has the mark, at its end on the map, at the foot of its page, in its head, in the map's summary and in Recent. Merged and archived lines say what became of them instead.

**The counts over a line's page are filters**, with the home's look: working, stopped, to review and finished Works. Pressing one shows only those Works, each with the Ask it answered, on the page and down the side, and pressing it again shows the whole line. They stay at the top as the page scrolls. A Work marked while a filter is on stays in view until the filter changes, and anything new on the line shows anyway. The panel's arrows step through what is shown, and going to a Work the filter hides shows the whole line again. The filter is in memory only.

**Refer** on an Ask, or at the end of a Work's detail, quotes it in the line's box, so "fix it" says what to fix. The new Ask keeps the quote above its words and on a line of its own in the Markdown (`> Refers to [Work 39](slug/work-39.md): …`). Either paste button, and a run from here, tells the agent what it refers to: an Ask's words and pictures, or a Work's short note and the path of its detail file, whose full text is not passed. It is told as background, "For context only, not a new request", with each quoted line marked `>`, so the agent does not take the earlier words for a new request. It comes before your words, so they are read last, as the request. Pressing the quote goes to what it refers to.

**Copy** on an Ask, beside Refer, and on a Work's detail, on the Reading and Source row, takes the raw text: what the Ask says without what apps wrap around it, or the Result's Markdown as Source shows it, from either view. Text and attachments have a button each, **Copy text** and **Copy the picture** (or **Copy 2 pictures**), for two pastes, because no agent's box keeps both from one. The second needs a Mac and the computer running PenEcho; anywhere else there is one **Copy**, and the text lists the files' paths. An Ask not sent yet has the two Paste buttons instead.

Every copy on these pages goes straight to the clipboard, by whichever way the window allows: the page's own clipboard, then the computer running PenEcho (`POST /copy`), then the browser's older copy command. An embedded window such as the Claude desktop app's Browser pane denies the first. The box to copy by hand opens only when all of them fail.

A quote alone in the box goes along with the Paste of an Ask already waiting, and moves from the box onto that Ask. With words or files beside it in the box, it stays with those.

**Run with X** comes first on the Ask, and is the filled button: PenEcho runs that agent itself, with no paste, on this computer or from another device. X is the agent you picked for this line, else the one that last worked on it (`lastWorker`), else the project's usual agent. The arrow beside it lists every agent PenEcho can run under Run with, the current one ticked, and picking one runs it. An agent with only its app, such as Kimi without Kimi Code, is not listed, and the server refuses it. With one such agent there is no arrow. What you type never changes what the box does. The other agents have no app, so the hint gives the command to run instead.

PenEcho never writes into a conversation that its app holds, because the app would not see it: `claude -p --resume` on a conversation open in Claude desktop writes a copy beside it. Claude says which conversations a process holds (`claude agents --json`, read by `agents.openNow`). For the others, a conversation PenEcho did not start, or one you carried on in the app, stays the app's (`heldElsewhere`). Run then starts a new conversation that reads the line, and the page says so. A conversation PenEcho started and nobody else holds carries on. A finished run is left alone: nothing opens in the agent's app until you ask, so the next Run with Claude carries on the same conversation.

## Which branch a new line works on

The home's box always says which, in a chip beside Send.

- **If you choose nothing,** it is the latest branch with a line on it that is not merged. A question asked on main does not change that. With no such branch, it is a new branch from main. It is never main by itself. While you are writing, the choice stays put, however busy the agents are.
- **New line** on a branch's label, or on main, chooses that branch and puts the cursor in the box. It is the same quiet grey button everywhere: the chip beside Send already says which branch the box is set to. A merged branch does not offer it.
- **The chip** opens a menu: a new branch from main or from the current branch, the branches on the map with their lines and a dot if one is working, then the rest of Git's unmerged branches by date, with a search. Main is last and says "Straight on main".
- **Main** is only for the one line you chose it for. The chip is amber and says so. The box then goes back to the latest branch, and a branch you have just used is the latest.
- **A new branch starts when you paste,** not when you send, so an Ask you take back leaves nothing behind. Until then the line hangs under a dashed "New branch" label, and its file says `new branch from: main`. A name already taken gets a number.

What decides it is the folder. A branch can be open in only one folder, so Paste uses the folder it is open in, or makes one under PenEcho's `checkouts` folder. These count as the project's checkouts, so what happens in them is followed and they get the drawing skill. A new folder has no `node_modules` or ignored files, and uncommitted changes elsewhere are not in it.

An app cannot always start in that folder: Claude's takes a folder under `.claude/worktrees` as its main checkout. So what you paste also says `Work in <folder>, on branch <name>.` PenEcho removes that line when the message comes back, so it never counts as your words. Back into a line's own conversation it is left out, because that conversation is already where it works. A conversation you start directly in an app is followed as it is: PenEcho only knows its branch afterwards.

**Without Git** the page is the same with no branches: one line down the page named after the project, no chip, labels, Merge or counts, and work goes straight in the folder. A repository with no commit yet counts as this, because no branch can start from nothing. If the project has a code folder, **Track changes** asks first, then runs `git init` if needed and commits the folder's files, leaving out `node_modules`, `.env` files, keys and `.penecho` through `.git/info/exclude`. Nothing leaves the computer. If that fails, a repository it made is taken away again.

## The drawing skill

An agent you talk to in its own app knows nothing of the Canvas, so asked to draw it gives you text art or Mermaid. PenEcho's background runs are told in their prompt, and a pasted request points at the README, but something typed straight into the app needs the agent to find it by itself. A skill does that: agents read only its one-line description until someone asks them to draw.

- **Where:** `.claude/skills/penecho-canvas/SKILL.md` for Claude Code, and `.agents/skills/penecho-canvas/SKILL.md` for Codex, OpenCode and Pi. These agents search only up to the root of the checkout they are in, so it goes in the docs folder, the code folder and every other checkout of that repository, and new checkouts get it within a minute. PenEcho's own run folders do not. dsh is not covered.
- **Out of Git:** the paths go in the repository's `info/exclude`, so there is nothing to commit. Nothing goes in `AGENTS.md` or `CLAUDE.md`.
- **What it says:** first, send the file to the PenEcho running on this computer with one `curl` (read `~/.penecho/draw.json`, post the file and the folder, read back the picture's path; see "Drawing with no setup"). Only when that cannot be reached, write `name.diagram.json` or `name.explorer.html` in `.penecho/drawings/` of the folder the agent is in, so it needs no permission for another folder.
- **Once for every project:** `GET /api/lines/agents/skill` says whether the user-level copy is in `~/.claude/skills/penecho-canvas/` and `~/.agents/skills/penecho-canvas/` (`{ installed, places:[{ path, state:"installed"|"outdated"|"missing"|"yours" }] }`); `POST` with `{ install:true }` writes it there, `{ install:false }` takes it out, and both answer the same report. Only from the computer running PenEcho (`{ unavailable:true }` otherwise). A `SKILL.md` PenEcho did not write (no `Written by PenEcho` mark) is never changed or removed. Its fallback says the drop folder works only in a folder of a project with its own drawing skill on, since only those are collected.
- **What PenEcho does:** it checks the file. A small guess is forgiven, such as a node type of the agent's own, because the agent may have finished by then. A file it cannot use gets `name.diagram.json.error.txt` beside it, saying why, and a note on the Topic. A good one goes to `files/<topic>/` of the conversation whose tool calls wrote it, or else of the one most recently at work in that folder, or `files/drawings/` if there is none, and becomes a picture like any other. Writing the same name again updates the picture.
- **Which Work shows it:** the one whose tool calls wrote the file, even if another agent's Work is newer on that line. While two Works are open and neither has been heard writing it, the picture waits up to 20 seconds for their conversations to catch up. After that it goes on the latest Work.
- **Adding and removing:** a new project offers it on its home, with why. Until it is added there is **Add drawing skill** at the top right. Settings removes it, which takes out only the files PenEcho wrote and its lines in `info/exclude`. A skill of your own with that name is never touched.

## Opening a Canvas

**Edit on canvas** grows the picture to fill the screen, and its Canvas opens under that same picture. `public/project-lines-cover.js` puts the cover up before the page paints, so the Canvas the page would otherwise bring up first is never seen, and `project-lines-bridge.js` lifts it once the right Canvas is ready and fitted to the screen. Leaving by Done or Back puts the cover up again before the Canvas closes, for the same reason.

## The home's lines

Each line on the home lists at least the latest two Asks and two pieces of work, in words, and where it stands now. What it leaves out is one small count that opens the same page. Pointing at a stop shows what it says in full, with its pictures.

`main` is one hairline down the left, the darkest of the tree, with the days beside it. Everything else hangs off it at the same weight, oldest at the top, lines and branches mixed by date:

- A line on `main` leaves it directly.
- A branch is a label on its own line, saying its name, how many lines it has, its size, **Archive** and **Merge**. Its lines hang under it. The label's **Archive**, at the right just before Merge, archives every line on that branch and on the branches off it, also those a count filter hides, and one **Undo** brings them all back. Like a line's own Archive, it stops any of them that is running and leaves the Git branches alone.
- Archive asks first when it would take a branch's last line while the branch has commits not yet in where it merges to (its parent branch, or main): **Archive without merging?** lists each such branch with its commit count, then **Cancel** and **Archive anyway**, plus **Merge first** when it is one Finished line, which opens that line's Merge. Merged branches, lines with no branch, branches with nothing of their own, a branch another line still keeps on the map, and a branch Git has not reported on yet archive at once as before. The count is `ahead` in the map's branch tree.
- A branch from a branch leaves its parent, not `main`.

`src/server/project-lines/branches.js` works out how the branches relate from Git, and looks again only when a branch tip has moved. A branch merged into another hangs from that one and says so. Otherwise a branch hangs from the one it shares the most commits with beyond `main`, and because Git keeps no record of which of two came first, the older line counts as the parent. A label can say `Same commit`, `4 more commits`, `No commits of its own`, `Merged into x` or `Not in Git`. Only a branch with commits to merge offers **Merge**. Either choice it opens, Whole branch or Only this Topic, and an arrow drawn on the map, starts a new line on that branch (front `merge of`; the Topic gets `merge by`) and opens it. Its only step is a normal Ask, Not sent, with the whole merge and its safety rules in its words: you run it, paste it or edit it like any other Ask, and nothing merges until you do. When Git shows the merge, the new line and the Topic it merges both say Merged. A merge line offers no Merge of its own and does not count as another Topic on the branch. Clicking again while its Ask is still not sent replaces that Ask in the same line; throwing it away closes the line and leaves nothing waiting to merge. Lines on a branch that has nothing left to merge offer **Archive**.

Colours mean the same thing everywhere: blue is what you asked, teal is an agent's work, which turns while it runs, green is finished, amber is waiting for you, violet is what you have not read yet, red is only what failed or was stopped, and grey is not moving. The tree is one hairline, as thin as a line's own track: near black for `main`, slate for a branch, slate again for a line's track, so only colour ranks them. A branch's label is near black, the same ink as `main`'s. Pointing at a line or a branch lights its way back to `main`. Your words show without what an app wrapped around them when the conversation was read back, such as its context blocks, an interrupted marker or an attachment note; the Topic file keeps them.

Each kind of hint has one set of colour tokens in `public/lines/lines.css`, and a new kind of hint gets its own set there first:

| A hint says | Tokens | Colour | For example |
| --- | --- | --- | --- |
| Waiting for you | `--hint-you` | Amber | Answer, Not sent, To review, the count on a project |
| Not read yet | `--hint-new` | Violet | Unread, the unread count on the map |
| Working | `--hint-run` | Teal | Working |
| Finished | `--hint-done` | Green | Finished |
| Stopped or failed | `--hint-bad` | Red | Stopped |
| Not moving | `--hint-still` | Grey | Paused |

Each set holds the words, a `-soft` fill and a `-mark` for a dot or badge. Waiting for you and Not read yet also have `-label`, the fill of the one label a line can carry before its title.

Every line offers **Archive** when you point at it, and its `…` menu provides copy, rename, open folder and delete commands. A finished line whose branch has something to merge also offers **Merge**, under Archive. It starts the same merge as the branch's label, and a merge takes the whole branch, so while one is planned every line on that branch says In plan. On a line's own page **Archive** is a button in the open, first and left of **Merge**, whatever the line is doing; **Back to lines** takes its place on an archived one. The `…` menu there repeats neither. Archiving or merging takes it off the home, and **Archive** in the project's bar lists it, saying what became of it: Merged into `claude/project-lines`, or Archived. Anything in the archive has **Back to lines**, which puts it back on the home and keeps what it says about being merged. More words in an archived conversation bring its Topic back by themselves. An explicitly deleted Topic stays deleted; its former conversation can be handed off to a different existing Topic.

## Pictures

Claude Code, Codex or any other agent asks for a real Canvas picture by writing one small file in `files/x/`, in the same way the `projects-v1` branch writes native diagrams into Canvas files:

- `name.diagram.json` for an architecture, sequence or workflow diagram: `{"type":"architecture","title":"T","nodes":[…],"edges":[…]}`.
- `name.explorer.html` for a Visual Explorer: one self-contained page.

PenEcho, not the agent, then makes `name.penecho.json`, a real Canvas with the diagram as an editable Widget, and `name.png`, and links the picture from the Topic. So this needs no open browser, no network and no write access outside the docs folder, and it works inside any agent's sandbox. Diagrams are drawn on the server with the same layout code the Canvas uses. A Visual Explorer's picture comes from a local Chrome, cut off from the network, or is a plain title card without one. Updating the file updates that Widget in place and keeps everything else on the Canvas, also while that Canvas is open and being saved by its page (see Canvases in projects). A file PenEcho cannot use goes back to the agent once, with the reason.

On a Topic's page, clicking a picture opens it to view, whether or not it has a Canvas file. **Edit on canvas** opens the real Canvas where there is one.

A picture you sent is shown with your words: Claude Code's and Pi's are read out of the transcript and dsh's out of its own attachment store, and all are kept in `files/x/`. Older Topics that only counted them (`[2 pictures]`) are filled in once from the same place, without starting any work. Codex and OpenCode pictures that reach PenEcho only as a count are still only counted. Clicking it opens a large preview; **Edit on canvas** opens a new Canvas with the pen ready. **Draw** in the box opens a blank one. A picture you pasted or attached in the box says **Click to draw on it**, and opens on a new Canvas the same way; what you draw takes its place in the box. Either way nothing is written until you draw, and **Done** brings the picture back to the box. It waits there: click it to edit it again, press Send when you are ready. Until it is sent it stays in `files/_incoming/`, and it is not one of the project's Canvases. When it is sent, the picture and its Canvas move into the Topic's folder together.

## Starting

An empty Canvas shows recent projects and Start a project in the middle. New project in the Projects sidebar opens the same panel, without the recent projects. The form is one field under another: the name, then the docs folder, then the code folder if there is any.

**Open existing docs folder…** under Create project brings back a docs folder PenEcho made before, here or on another computer (`POST /projects/import`, `importFolder` in `store.js`). The name comes from the `project:` line of its README.md or MEMORY.md, else the folder's name. The code folder is linked by itself when the README's `code:` line, or else the `code:` most of its Topics carry, is a folder on this computer; otherwise the project has none and you can add one later. Topic ids carry on after the highest one, so `PE-275` is followed by `PE-276`. Nothing in the folder is overwritten. A folder with neither a `project:` line nor any Topics is refused, so choosing a parent such as `~/Documents/PenEcho` does not make one project over all the others. A folder already in PenEcho opens that project, out of Archived if it was there.

**The docs folder is the project's own folder inside the base folder.** The base is the folder the project made last sits in, so new projects land beside it, and `Documents/PenEcho` in the home folder before there are any: `~/Documents/PenEcho` on macOS and Linux, the whole path such as `C:\Users\you\Documents\PenEcho` on Windows, where nobody writes `~`. The subfolder takes the project's name, or the code folder's name while the name is empty, which is also what the name field offers. The line under the field says where the base is.

Choosing or typing a docs folder uses it exactly as it is, with no subfolder added, and that line goes away. A folder PenEcho already knows reopens its project instead of making a second one. Emptying the field hands it back to the name when you leave it.

Only the controls take the pointer, so a stroke can start anywhere, even over the panel. It fades while you draw and goes away once there is ink. A shorter window shrinks the pictures first, then drops the prose and puts each picture beside its title. Examples stay in the menu and the Canvas sidebar, and the sidebar also lists your projects.

Clicking a project grows its picture to fill the screen, then opens it. Before a project has a picture, the card shows a small map of its work.

**Example projects.** A computer with no projects yet starts with four, listed in the sidebar with the code project first: **Weather app**, a code project with two lines, each on its own branch of a real Git repository (one fixes a bug, one adds a chart from a drawing, both Finished and not merged); **Linear algebra**, a math study with two lines of a drawing, notes in LaTeX, an Ask and a Work with an interactive picture; **Notebook**, two lines of notes and a drawing with no agent; and **Sales deck**, one line whose Ask attaches a spreadsheet (`sales-2026.xlsx`) and whose Work puts four slides on the Canvas and links `sales-review.pptx` to download. They are made from `src/server/project-lines/examples/` by `examples.js` (`seedExamples` on a registry that did not exist, `addExample` for one), with their times set a few days back and their files dated to match, and live in PenEcho's own folder (`<state>/project-lines/examples/`), so they never become the base for new projects (`baseFolder` skips `example`). An empty project's **Examples** row opens them; one that was removed or archived is brought back from its folder as it was left, or made if it never existed, so an existing computer gets them on the first click. Nothing in an example reads as Unread until it changes (`readExample`). Tests and the browser checks start empty unless `PENECHO_LINES_EXAMPLES=1`; `0` turns them off. The pictures are made by `scripts/build-project-line-examples.cjs` and checked in. Check with `test/project-line-examples.test.js` and `scripts/verify-project-line-examples.cjs`.

From another machine on the network, the page shows that computer's folders instead, with the same access check and the same guard on private folders as PenEcho Agent.

## Merging

Nothing merges by itself, and merging is not a step of the work. Finished code waits on its branch for as long as you like. It only merges when you choose to: press Merge on the Topic and confirm, press Merge on a branch's label or a finished line or draw an arrow on the map, and press Merge in the tray. A branch merges back to where it came from: its parent on the map, or `main`. Drawing an arrow to the line of `main` or to another branch chooses for yourself. The merge then goes on record as a step in the Topic file.

A merge is a real `git merge --no-ff` in your code folder. It refuses, and changes nothing, when:

- the code folder is on a different branch,
- a tracked file has uncommitted changes,
- the agent left uncommitted work on its branch,
- the merge would conflict (the merge is aborted).

Merging into another branch happens in the folder where that branch is open, or a new worktree if it is open nowhere. It refuses in the same way when that folder has uncommitted changes. After a merge to the main branch, the worktree is removed, the arrow is saved beside the Topic, and `MEMORY.md` gets a line.

## Memory

`MEMORY.md` holds what every agent on the project should know. Its page shows the file beside what agents saved themselves and the project's files.

- **What matters** and **Decisions** are written by people and agents. The box on the page adds to What matters. Nothing asks a pasted agent to write here yet.
- **Landed** gets a row when a line merges into the main branch. Finishing writes nothing. On every sync a row goes if its Topic has neither landed nor kept a commit, so it cannot drift, and anything else written under Landed stays.
- **What agents saved** is read as it is each time you come to the page. It is never copied into the docs folder, which can be shared. For Claude Code that is the notes in `<claude home>/projects/<folder>/memory`, where a worktree's notes sit under its main checkout. For Codex it is the task groups in `memories/MEMORY.md` whose `applies_to` names the code folder. OpenCode, Pi and dsh keep no project memory that could be read.
- **Project files** are `AGENTS.md`, `CLAUDE.md` and `GEMINI.md` at the top of the code folder, and the Markdown files changed on the branches of lines still open, the latest 12 lines.
- Saved notes and those rule files reach only the computer running PenEcho. Another device sees the branch documents, as it can on a line.

A Work's panel shows only what that Work made: a document chip only when the Work's own record says it changed it, and no pictures that nothing on the line uses. Removing an Ask takes its attachments off the line for the same reason.

## Project search

Choose **Search** in the project header to search every Line as you type. Enter runs the text search. Matches include your Asks, notes and drawings’ words, each Work’s result and agent activity. Archived Lines are labeled. Deleted Lines are excluded.

On this computer, choose a saved agent, then click **Ask** or press **Command+Enter** or **Ctrl+Enter** in the search box to get an answer with links to the relevant Lines. Asking creates no Line or Work. Clear the box to see **Saved answers**. You can reopen or delete them even if an agent is unavailable. **Ask again** gets a fresh answer when an agent is available. On Cloud, the same Search control opens text search.

- One or two words must all be there. A longer sentence leaves out words like "what" and "did" and finds what holds at least half of the rest. Letters are matched as written, so Chinese needs no spaces.
- Results are grouped by line, the best match first and then the newest, three to a line until **More**. **All**, **Your Asks** and **Agents' work** narrow them. The words found are marked.
- **Working**, **Stopped**, **Need you**, **Todo**, **To review** and **To send** narrow matching lines alongside the content tabs. To send includes any line with an unsent Ask. Need you shows lines waiting for your answer or choice; Todo shows finished lines you marked Todo; To review shows finished Works not yet reviewed, excluding lines that need you or are marked Todo. These use the same rules as Home. Press a selected status again, or Clear status, to show all statuses. Changing the query resets both filters. Background updates and loading the full project keep the search box, focus and caret in place.
- A click opens the line at that Ask, or at that Work with its panel open. Back returns to Search with the same words, because they are in the address (`#<project>/find/<words>`). Searches you opened are kept as Recent in this browser.
- It is plain text, read from the files each time and kept only while a file is unchanged: no index, no database, and no model. About 260 Markdown files and their activity logs take 20 to 40 ms once read, and 0.25 s the first time.
- `GET /api/lines/projects/<id>/find?q=&tab=all|yours|work&status=all|working|stopped|you|todo|review|send` filters before the 60-line and 12-hit limits. `filterVersion:1` and `statusCounts` give unique-line counts for the current query and content tab, independent of the selected status. The content-tab badges count hits within that status. Caps are stated beside the returned results. Old servers are filtered locally; incomplete responses show an availability note without exact status counts. A server from before Find returns 404, and the page then searches what it already holds: your words and each Work's first lines.

Check with `node --test test/project-line-find.test.js` and `PLAYWRIGHT_PATH=/path/to/playwright node scripts/verify-project-line-find.cjs`.

## The Canvas

Drawing a picture goes to the real Canvas at `/?linesProject=&linesCanvas=files/x/name.penecho.json&linesDoc=lines/x.md&linesTitle=&linesBack=`. `linesDraft=1` says the Canvas is for the box: its back link reads Done, and it opens with the pen. `linesSeed=files/x/picture.png` places that picture on it when the Canvas does not exist yet.

- Opening reads the bundle from the folder into a Canvas document.
- About every 2.5 seconds, once an edit has settled and no Agent turn is running, the bridge writes the bundle and the PNG back. The first picture saved is linked from the Topic.
- Leaving by the rail (or by Done, on a Canvas for the box) saves, closes that Canvas document, and goes there.
- If a save fails, the Canvas says so and keeps trying. The next open keeps your unsaved version instead of loading the file over it.

## Canvases in projects

The server side is `service.js`, `canvas-file.js`, `store.js` and `http.js` (check with `node --test test/project-line-canvases.test.js`). The pages are `public/lines/canvases.js` and `canvases.css`:

- There is no link from the Projects page to a Canvas by itself any more: **My Canvases** is the way to a Canvas.
- **My Canvases** is the first row of the rail, above the projects, with **Search** over it (the Find page of the project you are in). Clicking it makes the project the first time. Its **+** starts a new Canvas there. While you are in it, the rail lists its Canvases under it. It opens on its Canvases until one of them has become a line; then it has a Home like any project.
- **Canvases** is a tab of every project, after Home: every Canvas file in the folder, newest first, each with its picture, its name and the line it is on (or when it last changed). **New canvas** makes a Canvas with a folder of its own and opens it.
- A card's **More** menu: Open, Open its line, Rename, Move to… (the whole line when it is on one, to My Canvases or another project), Take off its line, Delete. Delete leaves an Undo in the toast and a **Deleted** list at the foot of the page with Restore.
- A line's own menu has **Move to project…**. A line with a branch of its own, or with work running, stays where it is.
- **The line beside the Canvas.** A Canvas opened from a project has **Notes & AI** in its top bar, where the Agent button was (`src/client/app/project-lines-bridge.js`; the Agent is off there, `canvasAgentBesideLine`). It opens a panel that is this page in its panel mode (`public/lines/embed.js`, `embed.css`): `/projects.html?embed=panel&canvas=<file>#<project>/line/<line>`, or `#<project>/newline` for a Canvas on no line yet. The panel shows one line and its box. A note or an Ask on a Canvas with no line makes its line with that Canvas as its first node (`canvas:` on `/yours`, `/unsent`, `/topics`), and the Canvas page takes the line into its address. Anything that would leave the line is handed to the Canvas page, which saves and then goes there. The server lets `projects.html` be framed by its own address only.
- **The rail beside the Canvas.** One rail everywhere: a project's Canvas has the Projects page's rail to its left, in place of the Canvas's own sidebar and its Back to project link. It is this page drawn with only its rail, in a frame: `/projects.html?embed=rail&canvas=<file>#<project>[/line/<line>]` (`public/lines/embed.js`, `embed.css`; the Canvas side is `project-lines-bridge.js`, with room made before the page paints by `public/project-lines-cover.js`). There is one rail, so a row added to it (`renderRail`) is here too, with no list of rows kept for the frame. The project is open in it and the Canvas's line, or the Canvas itself in My Canvases, is marked. The frame is as large as the window, so the rail is as wide as on every other page (280, 58 or 52 px) and tells the Canvas page its width; that page shows only the rail's part of the frame, and all of it while a menu or a dialog opened from the rail is up. In this mode the page draws no view, reads no line, keeps no route, and leaves the boxes, a drawing on its way back and the memory notice to the whole page. Anything that leads somewhere (`go()`, an address change such as `#setup`, a plain link, another Canvas) is handed to the Canvas page as `{ leave }`, which saves the Canvas and then opens it in the whole window; `{ hide }`, `{ width }`, `{ over }` and `{ say }` (a toast) are the other things the frame says, and the Canvas page says `{ line }` when its Canvas becomes a line. **Hide projects** hides it and a button at the left of the Canvas's bar brings it back; the choice is the Projects page's own (`penecho-lines-projects-hidden`), so the rail is hidden or shown everywhere at once. A window under 900 px starts without it, and what is chosen there is for that visit. A Canvas opened to draw something for the box (`linesDraft=1`) has no rail and keeps Done. Check with `scripts/verify-canvas-rail.cjs`.
- **PenEcho opened by itself.** The Canvas page opened in the local app with nothing in its address (`/`, no parameters, no `#`) makes a new, blank Canvas in My Canvases (`POST /api/lines/my-canvases`, then `POST …/canvases { title }`) and goes to it, so it has the rail and is kept from its first stroke. A blank one made earlier that nothing was drawn on is used again. This happens only when the Projects pages answer on this server and the browser keeps nothing of the plain Canvas: no draft, no open document, no chat, no MCP connection. Otherwise, and for every address with a parameter (`?workspace=`, `?session=`, `?mode=companion`, `?playground=`…), the viewer, Cloud, a folder page and a guest Canvas, the page is as it always was. The working copies this browser holds of project Canvases are not drafts (`penecho-lines-docs`).
- **An agent's drawing on the open Canvas.** The page takes in the Widgets a save answers with, and every 4 seconds asks `canvas/pull` for what an agent drew since, when the pen is still. A Widget it already has keeps the place and size you gave it. Check with `scripts/verify-project-canvas-save.cjs`.
- Against a server from before these routes the page still opens; a new Canvas is made the old way (`files/canvases/canvas-N`) and the other actions say to restart PenEcho.

**A folder for each Canvas.** A Canvas of its own is `files/<name>/canvas.penecho.json` with `canvas.png` beside it, whether or not it is on a line. `POST /api/lines/projects/:id/canvases` with `{ title }` picks a free name and makes the folder; the Canvas page then saves into it as it saves any Canvas, so nothing is a Canvas until something is drawn (`blank:true` writes an empty one at once). It becomes a line when a note is added or AI is asked beside it: `canvas:"files/<name>/canvas.penecho.json"` on `POST …/yours`, `…/unsent` or `…/topics` writes `lines/<name>.md` with the drawing as its first node, and nothing else. No file moves, so a page that has the Canvas open keeps saving to the same file. Canvases kept the older ways are read as before: `files/canvases/canvas-N`, a line's `files/<line>/…`, and the box's `files/_incoming/`, which is still not one of the project's Canvases.

In the project's state each entry of `pictures` now also says `folder` (the folder under `files` it is in), `canvas:true` for a Canvas of its own, and `loose:true` when no line shows it and its folder is no line's. A Canvas of its own is called what its file says (`name`); any other goes by its file's name, or by the words under its picture on a line, until it is renamed.

**My Canvases** is an ordinary project for Canvases that belong to no other, made the first time something is written to it, as `My Canvases` in the docs base (`~/Documents/PenEcho`). `my-canvases` stands for it wherever a project id goes; `POST /api/lines/my-canvases` makes it and returns it. It carries `myCanvases:true` in the project list and in its state, and the list says its id. It cannot be archived or removed.

**An agent's drawing and your edits on the same Canvas.** A Canvas file says which text each agent-made Widget was last drawn from: `manifest.extensions["penecho.lines"].sources = { widgetId: sha256 of the source file }`. The Canvas page hands that field back as it read it, and older versions ignore it.

- A source file is drawn again only when its text is not the one the Canvas says it holds. So a source that did not change never replaces what you changed on the Canvas, whatever the files' times say, and a Widget you deleted stays deleted until its source changes. A Canvas made before this was kept is told the old way (by file time, a slide by its content) until it is next drawn.
- One thing at a time happens to a Canvas file: a save from its page, a picture being made, a rename each wait their turn (`withCanvas`).
- A save first draws any source the Canvas does not hold yet, then puts every Widget an agent drew since the page read the Canvas into what the page sent, where and as large as the page has it, and answers `changed` (their ids), `widgets` (the Widgets themselves) and `sources` (the field as it now is), so an open page can take them in. Everything else in the save is the page's. The picture the page sent with such a save was drawn before it had the agent's drawing, so the picture made with that drawing stays until the page sends one that shows both.

**Rename** (`POST …/canvases/rename` `{ path, title }`) changes the name in the Canvas file and under its picture on every line that shows it. A page that opened the Canvas before the rename keeps the new name when it saves, and is told it (`name`).

**Delete** (`POST …/canvases/delete` `{ path }`) moves the Canvas, its picture and the files it was drawn from to `.trash/canvases/<id>/` and takes it off the lines that showed it. It is listed in the state's `deleted.canvases` for a week. **Restore** (`POST …/canvases/restore` `{ removed }`) puts all of it back where it was, the drawing on its line included, unless something else has taken its place.

**Off its line** (`POST …/canvases/loose` `{ path }`): the Canvas, its picture and its source files move to a folder of their own (`files/<name>/canvas.*`) and the line keeps everything else. A line left with nothing on it goes to Deleted.

**To another project** (`POST …/topics/<line>/move` `{ to }`, where `to` is a project id or `my-canvases`): the line's Markdown file, its work details (`works/<line>/`) and its `files/<line>/` are copied there and only then removed here, with its activity and what was taken off it. It gets an id of that project and `moved from:` in its front matter, takes the next free name if its own is taken, and the next work on it starts a new conversation there. A Canvas on no line yet moves the same way, by its folder's name. A line with a branch of its own stays where its code is.

Delete, Off its line and the move are refused while that Canvas is being saved. Afterwards a page that still has the Canvas open under its old place is told where it went (`409 MOVED` with `moved`, or `410 DELETED`) instead of making a second Canvas there.

**The old Library in My Canvases (B2).** `GET /api/lines/library` lists every Library Canvas this server can reach: its own (`server:<id>`) and, signed in, the account's Cloud Canvases (`cloud:<id>`), as `{ canvases:[{ from, title, kept:"server"|"cloud", updatedAt, project:{ id, name }|null, imported }], cloud:{ signedIn, error? } }`, newest first. `project` is the old Canvas project it sat in (none for Uncategorized); `imported` is true when a Canvas in any project already came from it. Canvases kept in a browser are not listed; the page sends those with their content. `POST …/canvases { from, title? }` with no `source` fetches a `server:` or `cloud:` Canvas and copies it in (401 `SIGN_IN` for `cloud:` while signed out, 404 for an unknown one, 400 `BAD_FROM` for any other kind without content); the old project's name is kept in the file as `penecho.lines.group` and the state gives `group` on that picture. Asking again for the same `from` returns the Canvas already brought in, in whatever project it is now (`existing:true`, plus `project` when that is another one), and writes nothing, so the Canvas page may ask on every save. `POST /api/lines/projects { name, fromGroup }` makes a project (in a free folder beside the others) and moves every Canvas of its own in My Canvases with that label into it, each as a Canvas of the new project: `{ project, moved, failed? }`.

**From the Library** (`POST …/canvases` with `{ source, title?, png?, from? }`): `source` is the Canvas as the Library keeps it (a version 2 snapshot bundle) and is kept as sent; the Library's copy is not touched. `png` is the full picture as a PNG data URL when the Canvas is open. Without it, the small preview the bundle carries becomes `canvas.png`, and the full picture arrives the first time the Canvas is opened and saved in the project. `from` names where it came from; the same `from` again returns the Canvas already there.

## Drawing with no setup

An agent puts a picture on a Canvas the person can see and edit with one call, and no session, no open page and no MCP: `src/server/draw.js`. Check with `node --test test/draw-api.test.js`.

**Where agents find it.** At start PenEcho writes `~/.penecho/draw.json` = `{ "port", "token", "url" }`, mode 0600. The token is made once and kept in the state folder (`draw-token.json`), so it survives restarts; the port is the one this start listens on. Tests write `PENECHO_DRAW_FILE`, or a file in their own state folder under `NODE_ENV=test`, never the real one. With two PenEchos running, the one started last is in the file.

**Who may call.** Loopback addresses only, with a `Host` of `127.0.0.1`, `localhost` or `[::1]` (a rebinding name gets 403), no `Origin` header other than this same address and no `Sec-Fetch-Site: cross-site`/`same-site` (403 `CROSS_SITE`: a page of another site can neither post a form nor read an answer), and the token as `x-penecho-token` (401 `BAD_TOKEN` when missing or wrong). Bodies up to 64 MB, as uploads; what the file may hold is checked as for the file-drop.

**`POST /api/draw`** (multipart, so `curl -F` works):

```
curl -s http://127.0.0.1:3888/api/draw -H "x-penecho-token: $TOKEN" \
  -F folder="$PWD" -F file=@/tmp/map.diagram.json [-F title="How it flows"] [-F canvas=map] [-F line=fix-login] [-F new=1]
```

- `folder` (required): an absolute path to an existing directory. It picks the Lines project whose docs folder, code folder or a checkout of its code (PenEcho's own run folders included) holds it, the closest one first; archived projects are skipped. Otherwise **My Canvases**, made if needed. `project` (a project id, or `my-canvases`) may stand in for `folder`.
- `file` (required, exactly one): `name.diagram.json`, `name.explorer.html` or `name.slide-NN.html`, with the same rules and forgiven guesses as the file-drop. Nothing is written when it is refused (400 `BAD_FILE` or `BAD_PICTURE` with the reason).
- Without `canvas`, the file's name is the picture: the first time it becomes a Canvas of its own, `files/<name>/canvas.penecho.json` (a free name if that folder is taken), and the same name again (a deck's next slide, or a changed diagram) updates that Canvas. With `line`, or when the folder is a run folder of one line or the one line at work there lately, a new picture goes on that line instead: `files/<line>/<name>.penecho.json`, linked from the line as the file-drop does. Which Canvas a name made is kept in the state folder (`draw-canvases.json`).
- `canvas`: a name an answer gave (also any Canvas `GET` lists), to put this file on that Canvas. 404 if it is gone.
- `new=1`: with `line`, a new Canvas on that line (a free name beside the ones it has) even when the line's Ask came from a Canvas. For a person who asks for a new Canvas from inside one.
- `title`: names a Canvas made by this call.
- The Canvas is made by `Service.pictureFrom`, the file-drop's code, under the Canvas's lock (`withCanvas`), so it never lands inside a page's save, and an update keeps everything else on the Canvas: the person's ink, their Widgets, and where they moved the picture. An open page that saves an older copy keeps it too (Canvases in projects). The same file twice changes nothing. A diagram and a page sent under one name are one Widget, so the newer one replaces the older one's source file.

Answer:

```json
{ "project":"<id>", "projectName":"App", "canvas":"map", "line":"", "title":"How it flows",
  "path":"files/map/canvas.penecho.json",
  "url":"http://127.0.0.1:3888/?linesProject=<id>&linesCanvas=files%2Fmap%2Fcanvas.penecho.json&linesTitle=How+it+flows",
  "png":"/Users/me/Documents/PenEcho/App/files/map/canvas.png", "updatedAt":1762750000000 }
```

`url` opens the Canvas in the app (`linesDoc` is added for a line); `png` is the absolute path of its picture. Errors: `{ "error", "code" }` with 400 `BAD_FOLDER`/`BAD_FILE`/`BAD_PICTURE`/`BAD_CANVAS`/`BAD_REQUEST`, 404 `BAD_FOLDER` (no such folder) or `NOT_FOUND` (no such project, line or Canvas), 413 `TOO_LARGE`.

**Plot a function on a Lines Canvas.** A multipart POST can carry a JSON `plot` field with the exact project and Canvas. Give each new curve its own stable `artifactId`. To update it, reuse that ID. This example adds a graph beside an existing expression plot and inherits its scale and widget dimensions. For older hand-written widgets, supply the range explicitly when a match matters.

```sh
curl -fsS "$PENECHO_DRAW_URL" -H "x-penecho-token: $PENECHO_DRAW_PASS" \
  -F "project=$PENECHO_PROJECT" -F "line=$PENECHO_LINE" -F canvas=sketchpad \
  -F beside=widget-123 -F 'plot={"artifactId":"tangent","expression":"x*tan(x)"}'
```

For a first plot, omit `beside`. Expressions and optional numeric range pairs use the saved `penecho_plot` renderer. The response includes `widgetId`, saved `bounds`, and `view` (`live` or `saved`). With a recent viewport, `visible` means any overlap and `fullyVisible` means the entire widget fits. Both are null without a live rectangle. Read `preview.png` when `preview.ready` is true. A capture failure leaves the drawing saved and reports an unavailable preview. Initial placement takes the current viewport into account for graphs, explorers and diagrams. Content updates retain existing geometry.

**`GET /api/draw?folder=…&canvas=…`** answers `{ png, updatedAt, url, name, title, line, path, project }` for that Canvas as last saved: the picture the page saved, with what the person drew (while an agent's newer drawing waits for the page to take it in, the picture made with that drawing). Without `canvas`: `{ project, projectName, canvases:[{ name, title, png, updatedAt, url, line, path }] }`, newest first (every Canvas under `files/` but the box's `_incoming`). Looking never makes My Canvases (`{ project:"", canvases:[] }`).

**What changed, for an open Canvas.** `POST /api/lines/projects/:id/canvas/pull` with `{ path, sources, name? }`, where `sources` is the page's `manifest.extensions["penecho.lines"].sources` and `name` its `manifest.extensions["penecho.lines"].name`, answers `{ widgets, sources, name }` in the shapes a save answers: the Widgets an agent drew since the page read the Canvas (whole Widget objects, at the folder's x/y/w/h: a page that already shows one keeps its own place for it), the field as it should now be, and a name given elsewhere (`""` if none, or if `name` was not sent). It writes nothing and waits for the Canvas's lock like a save. 404 if the Canvas is gone. A drawing still waiting as a file-drop is not drawn by a pull; the next save or the next look at the project draws it.

**Asked beside a Canvas (B1).** An Ask sent with `canvas` keeps it on a line of its own under its words, `> On the Canvas [Title](../files/<x>/canvas.penecho.json)`, so its run, a retry and a follow-up know it; the state shows `canvas` on that Ask and on the work that answers it. The latest sent Ask decides a line's Canvas. Before a run on such a line its picture is made fresh, the prompt says which Canvas the person has open (its file, its picture, and the call that draws on it), the picture goes with the Ask's files, and the run's environment carries `PENECHO_LINE` and `PENECHO_PROJECT`. A drawing dropped in `files/<line>/` for that line, and `/api/draw` with `line=` and no `canvas`, go onto that Canvas as one more picture: the file becomes `<canvas>+<name>.<kind>` beside the Canvas, its own Widget, and the same name again updates it. `canvas=` with a name other than the Canvas's own does the same; with the Canvas's own name it updates its picture. `new=1` makes a new Canvas on the line instead. The prompt's call carries `line=` too, so an agent that leaves out `canvas` to make a new Canvas still puts it on the line. A Canvas that already has a picture keeps it until its page saves one with both; the answer's `png` is then the picture just drawn and `canvasPng` the Canvas's.

**A Widget keeps its file.** A change sent with `widget=<id>`, or as `<canvas>+widget-N.<kind>`, goes into the file that Widget already has: the Canvas's own page stays `<canvas>.explorer.html` (so Open page stays), one more picture stays `<canvas>+<name>.<kind>`, and a slide stays its slide file (a page without `data-penecho-slide` is refused there). Only a Widget drawn on the Canvas itself has a `+widget-N` file. A Canvas left by an older version with its own page under `+widget-N` gets the name back, and its picture, the next time the project is looked at; nothing on the Canvas is drawn again.

**A picture that is behind its Canvas.** `manifest.extensions["penecho.lines"].behind` is true while `<canvas>.png` does not show all of the Canvas: an agent drew one more picture on it, or drew its own picture on a Canvas that holds more, or a page saved without its picture. `GET …/canvas` then answers `behind:true`, and the page that opened it, once it is still, sends `POST …/canvas { path, redraw:true, png, base, sources }`. Only the picture and `behind` change. It is not taken (`taken:false`) when another page has saved or an agent has drawn since.

**What a Work made, on its card (H2, PE-365).** `work-outputs.js` reads the links and the paths written under `## Result` in a Work's detail file. A Canvas of its own (a `.png` with a `.penecho.json` beside it, or a file it is drawn from) joins that Work's `pictures` and belongs to its line, unless the line already shows it, so a drawing sent without its line still shows where it was made. Anything else it points to is in the Work's `outputs:[{ kind, path, title, line?, code? }]`, at most 12 (8 pictures): a page, document, deck, spreadsheet, media or other file under `files/`, a picture (not one named as pasted), a Claude Artifact, another line, or a page in a code folder of the project or in its `.claude/worktrees` (`code:true`; not under `public/`, `src/`, `test/` and the like). Code, logs, JSON, the files a Canvas is drawn from, folders, what you attached and what the line already shows are left out. The page shows the pictures small and a card for each other output, which opens it: a document in the reader, a page or file in the viewer, an Artifact in a new tab, a line on its page. A code page opens in the browser of the computer running PenEcho with `POST …/topics/:slug/open-output { step, path }`, which opens only a path that Work lists (404 otherwise).

**MCP.** Local `penecho_draw`, `penecho_plot` and `penecho_present_widget` go through the same call when no page is connected: see "Drawing with no page open" in [mcp-setup.md](mcp-setup.md).

## Cloud projects on this computer (B3)

Signed in, the account button's `GET /api/lines/cloud/account` also gives `plan` (`free`, `starter`, `plus`, `pro` or `max`), `credits:{ available }` and `kept:{ projects, limit }` (Cloud's credits summary; each is `null` when Cloud does not answer). `GET /api/lines/cloud/projects` lists the account's Lines projects in Cloud as `{ projects:[{ key, name, lines, sizeBytes, updatedAt, here, id? }], kept, limit }`; `here` (with the local `id`) when a project on this computer syncs to that key. A project only in Cloud is used through Cloud: any request to `/api/lines/cloud/p/:key/<rest>` goes to Cloud's `/api/v1/line-projects/:key/<rest>` with the account's token, and Cloud's answer comes back unchanged (only those paths, only signed in). `POST /api/lines/cloud/projects/:key/copy { folder? }` keeps a copy on this computer: a project in that folder (default: a free folder beside the other projects), every file brought down and checked, sync on, `{ project, existed }`.

**Both ways.** A project kept in Cloud (`project.cloud.sync`; its Cloud key is its own id, or the key it was copied from) is synced every 60 s, and right after each run on it. One round is the sync core's `syncOnce` (`sync/engine.js`, `sync/plan.js`, `sync/merge.js`; see `docs/design/one-penecho/ARCHITECTURE.md`, A) over three adapters in `cloud-sync.js`: this computer's documents folder (hashes cached as before; a file sync replaces goes to `.history/sync-<time>/` first, one it removes to `.trash/sync-<time>/`), Cloud's device-sync routes (the manifest with `?since=<rev>`, blobs, and one `POST …/commit { rev, put, remove }` that Cloud applies whole or refuses as `409 stale`), and what both sides agreed on, kept in PenEcho's state folder (`project-lines/cloud-sync/<id>.json` and a folder of agreed texts, Canvases included, for merging), never in the project's folder. A line's file and other text are merged by the core; a Canvas by its parts (each Widget, tile and picture). Two Works made on two sides with the same number (and so the same detail file): the piece that came from Cloud is renumbered to the next free number, its link follows, and its detail file is kept under that number. When a merge cannot decide, both are kept: ours stays, Cloud's is written beside it as `<name>.cloud-<yyyymmdd-hhmmss>.<ext>` (never synced), the state lists `conflicts:[{ path, otherPath, line?, at }]`, and `POST /api/lines/projects/:id/conflicts { path, keep:"mine"|"theirs"|"both" }` settles it (`mine`: Cloud's copy to `.trash/`; `theirs`: Cloud's takes our place, ours to `.history/`; `both`: Cloud's becomes a file of its own under a free name, answered as `kept`). A project removed in Cloud stops syncing here and keeps every file. A project this computer pushed before sync went both ways starts from Cloud's list as what both agreed on. Cloud's answer to turning sync on is passed through as it came (a fourth project on a free account: 409 `project_limit` with `details:{ kept, limit }`). A free account's projects share its 200 MB in Cloud.

**One Ask at a time on a line.** Before a run on a project kept in Cloud, the line is taken there (`POST …/holds { line, where:<this computer's name> }` → `{ hold:{ id } }`), said to be still held every 30 s (`POST …/holds/:id/beat`; a 410 means it was lost, and the run stops), and given back at its end (`DELETE …/holds/:id`), after which the project is synced at once. If Cloud says `line_busy`, the Ask is kept as Not sent with `> Held · busy · where <place> · since <time>` (`held:{ reason:"busy", where, since }` in the state); each round asks for the line again, and an Ask that gets it is sent with that hold. If Cloud cannot be reached, the run starts anyway and the rounds merge both sides afterwards.

## Credits (B5)

PenEcho's own agent tells Cloud what its model calls are for: the model proxy adds `x-penecho-product: lines` to every call it passes to PenEcho Cloud (never to a model of your own key). Out of credits is a state, not a failure. Before a run on Cloud models PenEcho asks for the balance; with none left the run does not start. If Cloud answers 402 before the first step or in the middle, the proxy keeps that answer for the run and the run stops. Either way the Asks its Work answers go back to Not sent with their words intact and a line under them, `> Held · credits · balance 3 · required 40`, which the state gives as `held:{ reason:"credits", balance, required }` on that Ask (the line's `why` is "Out of credits"); a Work that had started stays, stopped, with what it did. `POST …/topics` and `…/topics/:slug/run-unsent` answer 402 with Cloud's body when the run could not start. Run sends it again once there are credits, and the held line goes. A run on your own key is never held.

## Safety

- Paths are checked against the docs folder, symlinks included. Uploads go only to `files/`.
- Files from a folder are served with a sandbox policy, so a file's HTML or SVG cannot run as this page.
- Reads need the same access as Canvas storage. Writes also need the page's own origin. Both are refused on hosted pages, and on any host or network the local server does not trust.
- Anyone allowed to use this PenEcho, by PIN or open access, can start these agents, as with the Canvas Agent. Claude Code runs with file edits auto-approved in the worktree and docs folder, plus everyday commands for building, testing and looking things up. Codex runs in its `workspace-write` sandbox. PenEcho's own agent gets the same folders and the same commands as Claude Code, and never the account token or an API key: see "Run with PenEcho" above. Signed in, its runs spend the account's credits.
- A saved file is never overwritten by a stale page: a changed file returns a conflict, your text stays on screen, and you choose. Earlier versions go in `.history/`.
- Removing a project from PenEcho forgets it and stops its agents. Your folder stays.
- A docs folder that has moved shows as not found, and is never recreated empty. Choose its new place to carry on.

## Task context and token evidence

The Line composer offers **New task** and **Continue this task**. Completed work defaults to a new independent task; an active message, an unfinished task, recovery and the next step of an existing approval/prototype workflow keep the task identity. The selected mode is saved with the Ask. Sessions belong to a Line, logical task, agent and work/review role. Missing, externally held or incompatible sessions start fresh. An interrupted legacy Work can recover its exact session; the next Work migrates to the current prompt policy.

Fresh sessions receive the complete current Ask and attachments, stable project instructions, the current Work/result path and a deterministic historical packet. Historical text is limited to 32 KiB of UTF-8 excerpts with original source paths; this is a byte cap, not a model token cap. The current Ask, instructions and subsequent file reads are outside it. Original records remain authoritative. Changing Work paths, naming and Canvas instructions travel in the actual message because resumed agents may retain their original system/developer instructions. Routing does not depend on guessing a provider's cache lifetime.

Each run writes `works/<slug>/<work>.context.json` (attempt manifests, source hashes and prompt hashes) and `<work>.tokens.json` (reported usage, attempts, request references and the startup comparison). Provider token counters are normalized to inclusive input with cache reads/writes shown as subsets. Unknown values remain unknown. Claude message snapshots are upserted by message ID and its reported invocation total replaces provisional request sums. Codex thread totals are attributed only through a known pre-attempt baseline; duplicate, unrelated and lower counters cannot inflate usage. Retries retain their task and count additional usage without repeating startup savings.

Work and Line views show an **estimated startup input reduction**: the preceding Work's last measured main request input minus the new task's first measured main request input, only with the same reported model, agent and configuration. Negative and zero differences remain visible. This is a comparison of recorded request sizes, not measured total-task savings, a counterfactual continuation or a fee discount. Historical Works without telemetry are not backfilled from bytes. Internal helpers are included only where the runner reports their usage.

Project Home shows the sum for Today, Last 7 days (default) or All time, with UTC dates, coverage, recorded usage and an explanation. Archive retains the saved evidence in this summary; deleted Line evidence is not reconstructed. **See calculation** opens the arithmetic and provenance in one activation and offers the usage and context JSON files. Evidence rendering and aggregation run locally with no model request.

Focused acceptance: `node --test test/project-line-task-context.test.js test/project-line-token-evidence.test.js test/project-line-penecho-runner.test.js` and `PLAYWRIGHT_PATH=/path/to/playwright node scripts/verify-token-savings.cjs /tmp/token-savings-shots`. Browser acceptance starts a temporary local server and fake agent, uses an OS-assigned port, and cleans up its own data and processes. It makes no external model calls.

### Line commands and reading updates

- **The app** must be the real one, in `/Applications` or `~/Applications`, read from its `Info.plist`: a plain ChatGPT.app does not answer `codex://`. Claude needs at least 1.1.9669, the floor Claude Code itself uses for these links. Codex needs 26.1103 for a new thread in a folder.

**OpenCode** opens in a terminal, because its desktop app acts on no link: tested on 2.2.5 with `opencode://open-project`, `new-session` and `session`, and its window did not change. The program inside the app (`Contents/Resources/opencode-cli`) opens the exact conversation, or a new one in the line's folder, through the same background service as the app. An older `opencode` on the PATH may say "Session not found" for what the app holds, so the commands PenEcho shows use the app's program too. A conversation counts only with a row in `session_v2`, not archived and not a helper's. A `.command` file opens the window, which needs no permission to drive Terminal, and removes itself. Pasting a picture there is left out: the paths in the words are what it reads.

A line whose conversation is with an agent PenEcho cannot find here also stays a copy, rather than starting a conversation with another agent.

**dsh** only copies. Its app accepts one link, `dsh://open`, which brings it to the front, ignores anything else including a later launch's arguments, and its web app reads no session from a URL. Its install here has no terminal profile.

Anything else opens nothing and looks exactly like a copy, and so does a page on another computer. The clipboard is written first, so a failure to open never loses it. **Paste without context** never includes it. A message pasted word for word into a conversation on another line still goes to the line whose Ask it is. Copying alone leaves the Ask marked Not sent.
