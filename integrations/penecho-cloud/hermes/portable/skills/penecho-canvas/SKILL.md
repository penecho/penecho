## Open beside the conversation

When the user explicitly names an existing Canvas, continue with that exact target. For a retained Cloud workspace, resolve requests about the current Canvas through workspace_status as described below. Preserve explicit local/desktop MCP choices. Otherwise:

1. Choose one unique, stable `sessionKey` for this conversation (use the host conversation ID when available, otherwise generate and retain a UUID). Call `penecho_open_workspace`. This creates or resumes a browser draft, not a saved Cloud document.
2. Retain `workspaceId`, `url`, `canvasUrl`, and the browser tool/tab identity. If `alreadyConnected` is true, reuse the existing tab and check status. If `launchState` is `opening`, `nextAction` is `wait`, or `url` is null, poll this same workspace according to `retryAfterMs`: a redeemed launch may still be initializing its browser draft. Otherwise open the returned single-use `url` once through one capability. Prefer the host's embedded browser alongside this chat. In Codex, when exposed, call `open_in_codex` with `{target:{type:"browser",url},placement:"right"}`. A `queued` response means that opening was accepted: inspect and reuse that pending tab instead of invoking an independent second opener. Use a fallback opener only after the first capability explicitly reports failure or is unavailable. On Claude desktop, use `preview_start` only when the actual toolset exposes it and its schema supports opening an existing URL. Otherwise use the host’s actual native browser opener; do not invent tool names or promise a side pane in CLI-only hosts. If no embedded browser is available, use the supported default-browser opener or show one clickable launch link. Never send the launch URL to an external web-fetch or search tool.
3. Call `penecho_workspace_status`. When `state` is `ready`, call `penecho_start_session` with its exact `startSession` arguments, adding the live schema's required `client`/`title` if needed. Wait for that call to succeed and retain its `sessionId` and `documentId` before drawing, presenting, uploading, or editing. Loading status alone never authorizes a mutation or supplies a usable session.
4. Follow `retryAfterMs` while the initial `launchState` is `opening`, for up to its 30-second initialization window, then use at most five further bounded status checks. Do not reopen a page merely because status is loading. Follow `nextAction`: launch tickets expire after 120 seconds. For `launch_expired`, automatically call `penecho_open_workspace` with the same key and navigate the retained tab, using the same browser tool, to the renewed URL without another user question. Allow at most two launch renewals within this opening attempt, then report the concrete blocker. `open_original_draft` means the retained document is missing from this browser's storage; use its original browser profile for recovery. Opening the same workspace in another page is supported: the latest connected page takes over, and the older page disconnects. Continue in the latest page with the exact ready binding; do not require a return to the older tab. Do not substitute an unrelated Canvas or open a new tab on every check.

The returned URL selects `mode=companion`: a narrow tool rail, visible Save action, and a reversible Full Canvas switch in the same tab. Leave the parameter intact through reconnects. Do not ask users to visit the Dashboard, enable an MCP toggle or copy a token for this automatic workflow. A legacy server without workspace tools can use explicit Canvas selection after explaining that automatic opening needs a server update.
