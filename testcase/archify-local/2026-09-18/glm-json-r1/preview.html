PenEcho MCP 架构：本地 HTTPS 画布通道

外部 AI 客户端（直连或经 stdio 桥）→ PenEcho Node 宿主内的接入/RPC/会话分派/共用画布操作 → 已 opt-in 浏览器中的画布文档与 Widget 沙箱渲染；另含 guidance 只读分支与可选 Cloud 设备通道。

外部客户端stdio 桥接进程PenEcho Node 宿主浏览器状态与存储Cloud（可选）

接入路径与发现

  • 桥接与直连客户端先试已知地址和共享发现缓存，再按需经 discovery-client.js / lan-discovery.js 发现，无需常驻发现守护进程
  • 支持直接 HTTPS 的 MCP 客户端与桥接汇入同一 /mcp 端点
  • 桥接端与宿主各有自己的信任/凭据资料，图中只画职责不写凭据内容

宿主内职责与端口

  • src/server/main.js 在本地宿主内创建 MCP service，复用本地宿主与配置
  • MCP HTTPS 优先 3922、13922、23922，冲突后可选空闲端口
  • 主 Web 服务默认 3888，与 MCP HTTPS 接入同属宿主配置

两种存储，所有者不同

  • 持久会话绑定由 Node 宿主持有并读写
  • 画布文档与快照由浏览器持有，不能画成 Node 文件存储
  • 工具的虚拟 source path 不是模型电脑上的真实文件路径

guidance 与内置 Agent

  • penecho_get_guidance 从规则 registry 按需读取对应文档并返回 id/hash/document
  • 本轮新增 architecture 独立规则；通用 visual-explorer 仅列规则目录，不含架构正文
  • 内置 Agent 的 document-tools.mjs 复用共用画布操作与 guidance，有自有会话绑定，不是外部 MCP 的必经环节

会话恢复与日志

  • HTTP 空闲清理不会终止 stdin 仍打开的轻量桥；下一次调用重连并恢复原文档，不盲目重放可能已提交的写请求
  • 开启请求日志时 request-trace.js 记录多轮 MCP tool/browser 交互，MCP 日志目录与 Agent 日志目录平行
  • 日志不是实际画布源文件

Cloud 扩展（可选通道）

  • 用户开启 Cloud MCP 后，浏览器经本地 /api/mcp/cloud-canvas 接入 CloudMcpBridge
  • 桥带宿主设备凭据连接 Cloud WSS /api/v1/mcp/device-canvas 并双向转发画布帧
  • 画布操作由 Cloud 的 MCP 运行时发起，不表示云端请求必须串过本地 HTTPS MCP 工具分派；未臆造云端数据库、队列或内部部署

结果、错误与截图沿实际请求通道逐级返回；图中仅显式画出浏览器 → 共用画布操作一段返回边。

宿主组内的方框是同一 Node 宿主内的职责分工，不是各自一台服务器；候选端口也不是多台服务器。

kind 为 optional 的双向边表示 opt-in 的 Cloud 通道，仅在用户开启后存在。

外部 AI 客户端有两条独立接入路径（stdio 桥 / 直接 HTTPS），二者汇入同一 HTTPS MCP 接入。
