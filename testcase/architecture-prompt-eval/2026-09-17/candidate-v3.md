## Architecture diagrams

For architecture diagrams/regions only. Other visual types keep their existing rules. Here, prefer a readable **component-and-relationship map** over the generic dense infographic/panel defaults below. The main drawing must explain who connects to whom without reading supporting prose.

1. **Select entities and boundaries.** Show actors, services, components and stores at a consistent abstraction level. Each entity has a short name and, if needed, one short role. Use simple shapes or meaningful icons. Put implementation paths, feature lists, parameters and explanations in a separate detail region keyed by entity name. Enclose meaningful subsystems, environments or responsibility domains with named thin frames; nesting must not invent process, deployment or trust boundaries.
2. **Represent relationships explicitly.** Preserve the important independent paths, branches and shared dependencies. Every edge identifies its actual source and target entity, direction and meaning. A group's position or a whole-layer arrow cannot substitute for these links. Use brief labels only when they add information; distinguish calls, data, events and returns consistently. Omit unsupported relationships.
3. **Compose freely, with shared geometry.** Choose orientation, grouping, view count and detail placement for this system; no fixed template or node count. Use a compact node table with stable IDs and bounds, and edges referencing those IDs. In the HTML, a small SVG helper can derive shapes, text positions and edge ports from those same bounds; do not independently guess/copy endpoint coordinates. Plan generous routing lanes and shared alignment guides. Route around unrelated nodes and frame titles. Keep peer labels aligned, arrows attached to the intended outline, and crossings distinct from junctions.
4. **Make it presentation-readable.** Let the topology occupy the useful space. Use short labels at normal readable sizes, regular gaps, consistent shapes/strokes and restrained semantic colors. Put detail outside the topology rather than squeezing it into nodes. Wrap long labels or allocate more space; do not shrink the whole page or distort SVG with nonuniform scaling. Output only the working figure, without hidden draft paths or explanatory SVG comments.
5. **Verify the graph and pixels.** Check each drawn source/target against the facts and the node table. Then inspect the actual render for node/label overlap, detached or wrong arrowheads, boundary mistakes, alignment and readable text. Revise the relevant geometry or wording. Success is a traceable, accurate map, not resemblance to an example or a prescribed arrangement.
