# 架构图 Prompt 实测记录

本报告记录真实 API 输出和 PenEcho MCP 像素审查。通用 Prompt 位于各版 `candidate-v*.md`；请求保留在对应 `.job.json` 和 `runs/*/request.json`。模型原始输出未被人工修饰后冒充合格样本。

## 从参考图提取的共性

- **实体承担识别，详情承担解释。** 主图使用短名称、简单形状或有意义的图标，文件名、参数和实现说明单独放置。
- **框线表达包含。** 子系统、运行环境、网络或职责域用有名称的边界表达；不把代码目录误当进程或安全边界。
- **箭头表达组件关系。** 独立入口、分支和共享依赖必须能从具体实体追踪，不能由层次上下位置或长说明代替。
- **布局服从拓扑。** 不规定方向、节点数、路径数或面板模板；先布置有连接的实体，再安排其他内容与详情。
- **颜色建立索引。** 主图组件与详情沿用同一语义色，同时保留名称；颜色不是装饰性编号。
- **几何影响可信度。** 先调整节点形成水平/垂直连接，再使用清晰折线；文字重叠、遮挡、错接是验收失败。

## 实验方法和边界

调用用户指定的 Anthropic 兼容端点，返回模型均记录为 `glm-5.3-flash`。API key 经不回显输入保留在评测进程内存；未保存授权头、密钥或隐藏推理正文。

完整指导各版只替换架构图段落，其余 Visual Explorer 指导、PenEcho 事实、模型参数保持一致。v4 另外比较了完整指导与独立架构指导：后者是上下文消融实验，尚未改动产品的加载逻辑。

从零生成的请求没有把参考图、完成的模板 HTML 或目标坐标交给模型，模型自由选择布局。另有三次明确标注的审图修正请求使用实际发现的缺陷和原始 HTML：一次超时、两次成功返回局部补丁。这些结果不能冒充从零生成的样本。

有效 HTML 原样经 PenEcho Cloud MCP 发布，截图按实际视口审查。比较视口为 1939×1134 CSS px，截图缩放为 1440×842；v1 初次视口不同，另做了匹配视口检查。截图不能证明未显示的下方内容不存在。透明区域在工具预览中可能显示为黑色，不代表模型选择了黑色背景。

## 目前已核实的发现

1. 在这些样本里，增加“对齐、避免重叠”条款并没有稳定改善结果。语义错误与像素错误必须分别核查。
2. 通用信息图要求可能与简洁的架构主图形成竞争。v4 独立指导样本更简洁，但仍有关系错误；一次对照不能证明因果关系或稳定性。
3. v4 对照的总输入为完整指导 4,463 tokens、独立指导 1,005 tokens；这包括案例事实和传输要求，并非架构规则自身的 token 数。时间分别为 138.91 秒、154.45 秒，不能据此声称简化 Prompt 已加速。
4. 节点/边共享数据有助于审查对应关系，但模型仍可能生成错误的边或有异常的脚本；数据结构本身不等于正确性。
5. `thinking.type=disabled` 请求中仍观察到 thinking 事件；初期两次 high 参数调用耗尽 16,000 输出 tokens，未返回 HTML。另有读取超时。此处仅陈述本次接口实测，不推断所有版本的能力。

## 本轮实测结论

本轮共执行 22 次 API 请求：10 次返回完整的初始架构图 HTML，2 次返回可精确应用的模型补丁，1 次为接口探针，9 次未返回完整可交付内容。未执行的 job 文件不计入结果。19 次取得最终 usage 的请求合计输入 59,522、输出 169,310 tokens；其余 3 次取消/超时的最终用量未知，不能记为免费或零用量。这些数字包含接口报告的思考/输出预算消耗，不等于 HTML 文本 token 数。

| --- | --- | --- |
| A 基线 | 59.76 秒；关系不完整、缩放/布局缺陷 | 不合格 |
| B v1 | 137.48 秒；出现明确组件连接与独立详情，但仍有溢出与可读性问题 | 有改善，未通过 |
| J v6 原始输出 | 129.81 秒，输入 1,316 / 输出 7,418 tokens；实体简洁、分组配色、正交路径，但有错接/缺边与标签问题 | 未通过 |
| K 第一次模型补丁 | 91.99 秒，5 处精确替换；修正模型调用起点、增加 Agent 模型关系与橙色详情 | 改善，仍有 MCP 标签碰撞 |

J → K → L 的三次调用共 275.99 秒，输入合计 12,526 / 输出 13,563 tokens；不包含渲染和人工审查时间。可以证实这条修正路径改善了该图，不能声称它已经满足“更快、更省 token”的目标。

L 仍存在较小字号、未充分使用的主图空间，以及“外部服务”框线同时容纳云端 API 与本地 CLI 子进程时的边界命名歧义。最后一排详情在本次视口下方，未进行像素验收。不得把“补丁已成功应用”或 MCP 的 pixelVerified 状态等同于完整专业演示验收通过。

电商分支案例的早期完整输出出现关系错误；后续输出达到 token 上限而不完整。RAG 请求超时，没有合格的跨系统样本。因此目前没有证据支持最终 prompt 的稳定泛化或一次生成合格率。

## 如何从修正中提炼通用 Prompt

提炼对象是错误的共同原因，不是示例的目标坐标：

- 由颜色断开对应关系，提炼为“主图与详情共享语义色及名称”。
- 由斜线和绕路，提炼为“连接相关实体共同布局，优先同行/同列，预留正交通道”。
- 由端点错接，提炼为“连线端点引用正确实体边界，布局变化时同步更新端点与标签”。
- 由标签重叠，提炼为“文字实际占用空间必须参与布局；不够时改位置、路径或文案，不覆盖其他信息”。
- 由卡片拥挤，提炼为“按可用宽度、实际文字和盒模型选择整齐的网格”，不规定所有图固定三列。
- 由内容堆砌，提炼为“实体识别、边界包含、箭头关系留在主图；实现说明归入对应详情”。

方向、分组方式、实体数量、配色选择和是否拆分视图继续由模型裁量。范围只限架构图区域。案例专用坐标、PenEcho 专用路径、固定列数不进入通用规则。

`candidate-v6.md` 是当前经过从零试验的候选规则，而不是已验证的最终生产 prompt。要求共享节点/边数据有助于检查，但这轮也出现模型忽略要求和 helper 抛错，不能简单把更多实现约束当成稳定性的保证。下一次收敛应从候选中压缩共性规则，用新的从零样本检验，并把单次生成与模型修正结果分栏统计。

本轮保留所有历史，停止 API 评测进程，没有将候选加入正式 lazy-load。正式契约有 16,000 UTF-8 字节加载上限，未来接入时还需核对长度，不能盲目追加完整候选。其他 Visual Explorer 类型、Archify/Mermaid 运行时均未因本轮实验改变。
