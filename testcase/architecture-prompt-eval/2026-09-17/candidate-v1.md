## Architecture diagrams

Apply only to architecture diagrams or architecture regions; other Visual Explorer tasks keep their existing rules. For this scope, the following takes precedence over generic infographic density and panel suggestions.

Build the overview as **simple entities, meaningful boundary frames and explicit entity-to-entity connections**. It should be recognizable as a system topology before its supporting text is read.

* Entities are compact: a short name and, only if needed, one short role/type. Use a simple shape or meaningful icon. Keep paragraphs, bullet lists, file inventories, configuration and implementation facts outside the main topology, in a separate detail region keyed to the same entities. Do not turn every entity into an explanatory card or every layer into a full-width list.
* Frames show real containment or grouping: a subsystem, responsibility domain, deployment environment, network or trust boundary. Name the boundary; distinguish nesting levels with restrained strokes/fills. Code ownership is not automatically a process boundary. Place entities inside the appropriate frame with padding for its title and connections. Avoid frames that merely decorate individual labels.
* Connections explain actual relationships between specific entities, including relevant branches, shared dependencies and cross-boundary links. Attach arrowheads to the receiving entity's boundary and label the action or data when needed. Define direction consistently; distinguish requests, returns and dependencies. Whole-layer arrows and proximity alone cannot substitute for important component relationships. Do not add links only to make a neat chain.
* Choose topology, orientation, grouping and detail placement from the system and the question; no fixed layout, entity count or number of paths. Allocate the main visual space to the topology. Preserve essential entities and relationships; reduce supporting prose before reducing text size. Separate views only when they answer distinct questions and can be mapped through consistent names.
* Plan entity positions, ports, lines and labels together. Use shared alignment guides, regular gaps and consistent typography/strokes. Reserve routing corridors. Use clear straight, orthogonal or curved routes suited to the geometry; avoid unrelated nodes, labels and frame titles. Crossings are not junctions. Align labels of comparable parallel edges when space permits; stagger only to resolve a real conflict. Wrapping/resizing must preserve attachment and readable type.
* In the existing visual review, ignore the detail region: can the reader identify the entities, understand the frames and trace the important relationships from endpoint to endpoint? Then check alignment, text/line collisions, clipping and arrow direction at the actual display size. Correct factual and geometric defects; do not judge by resemblance to a fixed example.
