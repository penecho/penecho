A传输入口

  • 桥接 session-client.js 读共享主机凭据与发现缓存，校验 TLS，HTTPS /mcp 复用连接
  • 端口候选 3922 / 13922 / 23922，冲突后选空闲 —— 仍是一个 HTTPS 接入
  • 发现按需进行，无常驻发现守护进程
  • HTTP 空闲清理不终止仍打开 stdin 的桥；重连恢复原文档，不盲目重放已提交写请求

B宿主内职责

  • direct-http-service.js：拥有 HTTPS listener、认证与传输会话
  • rpc.js 处理 JSON-RPC；schema.js 校验工具输入（与 guidance 同源）
  • 图片上传 /mcp/images 复用同一接入与认证，服务端有界处理后交给指定文档
  • 浏览器关闭授权后，宿主不再接受外部画布操作

C会话与绑定

  • service.js 持有已授权浏览器连接、打开文档目录与画布会话
  • conversation-bindings.js 持久化 client/sessionKey → canvasId/documentId
  • 浏览器连接 ID、文档 ID、业务 sessionId、HTTPS 传输 session ID 是四种不同标识
  • 内置 Agent document-tools.mjs 也复用共用操作，有独立绑定，非外部 MCP 必经环节

D浏览器执行

  • hello / 打开文档 catalog → 接收 call → 返回 result；心跳、断线、取消均有处理
  • penecho_present_widget 传入的 HTML 在沙箱 iframe 中渲染
  • 后续 read_file / patch_file 围绕同一文档的虚拟源文件，非模型电脑真实路径
  • 版本 / hash、幂等 requestId、虚拟读写由 bound-operations.js 协调

EGuidance 与日志

  • penecho_get_guidance 是 RPC 独立只读分支：读 authoring-guidance.js 返回 id/hash/document
  • 不进浏览器画布队列，也不调用模型
  • architecture 为独立规则；visual-explorer 只列规则目录
  • 开启后 request-trace.js 记录多轮交互；日志与画布源文件无关
