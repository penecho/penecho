# Architecture diagrams

Scope: architecture regions of the current artifact only. This rule replaces generic infographic density, feature-card and panel-count defaults there; shared runtime, accessibility and delivery requirements still apply. Other visuals and later tasks keep their own rules.

The result is a **readable relationship map with simple entities, named boundary frames and separate supporting detail**. Choose the viewpoint, orientation, abstraction and number of views from the system and the reader's question. There is no prescribed node count, layer count, column count or layout template.

## Author in this order

1. **Select the architectural story.** Identify the important actors/components/stores, their owners and the relationships needed to explain the question. Preserve branches and independent paths. Use the supplied implementation facts as evidence, not as a checklist of boxes to display. Leave secondary mechanisms in detail or a related view. A meaningful abstraction may combine steps, but must preserve their relationships.

2. **Establish topology before positions.** For each displayed relationship determine source, target, direction and meaning. Distinguish calls/control flow from data access and configuration. If A calls B and B reads store S, the edges are A→B and B→S, not A→S→B. A connection, response path and request direction are different semantics; name the chosen meaning consistently. Frames express real containment (responsibility, process, deployment or trust), not a decorative layer stack. Group membership never substitutes for a component relationship.

3. **Budget readable labels first.** Main-map entities have only two text slots: a short name and an optional single short role line. Do not add file names, paths or implementation bullet lines underneath; keep those in the matching detail. An exact identifier belongs in the main map only when that identifier is itself the subject of the question. Set text at its actual displayed scale before fitting the layout: main names normally 16–20 CSS px and edge labels 13–15 CSS px. Do not build an oversized viewBox and shrink it to fit. Use bounded text containers or explicit SVG line wrapping; account for actual font metrics instead of assuming a string fits. Shorten the label, increase space or choose another arrangement/view before reducing type size.

4. **Arrange around connections.** Align connected entities on shared rows/columns where practical. Prefer straight horizontal/vertical edges; use orthogonal routing lanes for necessary bends, optionally with small rounded corners. Move nodes before introducing detours. Reserve complete connection corridors, including labels, arrowheads and clearance from frame titles. Several inputs to one entity use distinct aligned ports or an explicit junction; a route must not double back alongside another input merely to reach the nearest edge. Comparable boxes, headings and parallel-edge labels share alignment guides and consistent spacing.

5. **Construct without disconnected geometry.** Keep entity bounds in one place and derive ports, edge endpoints and label locations from those bounds/route segments. Each edge must visibly reach its actual source and target outlines, including across frames; it cannot stop at a convenient frame or blank gap when a component endpoint is known. In SVG, paint boundary backgrounds first, connections above those backgrounds, and entities/text above connections. A later opaque frame must never erase an entering arrow. Keep the implementation small; no elaborate layout engine is required.

6. **Allocate space before drawing text.** Keep short horizontal edge labels beside a clear straight segment, away from arrowheads, bends and entity borders. Move long protocol strings to detail. Parallel labels use a common offset; nearby branches get distinct lanes. Check actual text bounds and padding, not just anchor coordinates. A label backing may interrupt its own edge only; it cannot mask another line, frame or entity. Paths avoid unrelated entities/text, and crossings must not look like junctions. Derive each frame from its children plus room for its title and internal routes. Put the legend and general notes outside all architectural frames, in normal document flow with a separate gap; never hang them on a frame's bottom stroke. An optional path needs real endpoints and correct ownership; move it to detail if it cannot be drawn clearly.

7. **Connect detail through color and names.** Define one semantic palette keyed by entity/domain identity; graph accents and matching detail headings, borders and badges all use that same key or CSS variable. Do not assign detail colors separately or cycle them by panel order. Keep detail outside the topology, under the corresponding visible entity/domain names. A cross-domain explanation is neutral or explicitly identifies its constituent domains. Color aids recognition; visible names remain necessary. Put each fact in its most useful place once; the supporting material need not reproduce the entire evidence inventory.

## Acceptance

Check two things separately before delivery: (a) trace the important routes and frame membership against the facts, including bypasses and branches; (b) check visible endpoints, drawing order, alignment, text bounds, clipping and readability at the actual host viewport. Essential labels that overlap, are covered or require magnification fail acceptance, as does a false/missing relationship. Simplify the abstraction or rearrange the view until both checks pass. The reader should understand the main system without reading the implementation detail.

When host rendering/capture tools are available, verify the first rendered result rather than assuming source inspection proves visual correctness. If a concrete defect is found, patch the affected source and verify it again; preserve working content and artifact identity unless the user requests separate comparison versions. Do not repeat captures for unchanged or purely cosmetic details. If rendering is unavailable, report that verification is pending rather than claiming the drawing passed.
