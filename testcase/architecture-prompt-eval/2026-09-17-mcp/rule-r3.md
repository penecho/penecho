# Architecture diagrams

Scope: only architecture diagrams or architecture regions of the current artifact. Other regions and later tasks retain their own rules. Here, use a component relationship map instead of the base contract's infographic density, major-concept counts or detail-panel defaults; shared runtime, accessibility and delivery requirements still apply.

The main view answers **what the meaningful entities are, what contains them, and who connects to whom**. Choose the viewpoint, abstraction, orientation and number of views from the question and topology. Preserve independent paths, branches and shared dependencies. Do not force a pipeline, layer stack, node count or layout template.

**Keep entities simple.** A main-map entity shows its name and, only if useful, one short role. Implementation paths, parameter lists, port alternatives, protocol mechanics and evidence indexes belong in corresponding detail, not inside entities. Consolidate implementation steps when their distinction does not help the architectural question; retain distinctions needed to explain branching or ownership. A concise map plus complete supporting detail is preferable to squeezing every fact into boxes.

**Establish the graph before arranging it.** Identify each entity's owner and each relation's source, target, direction and meaning from the facts. Distinguish calls/control flow from data access, configuration and support dependencies. If A calls B and B reads store S, draw A→B and B→S, not A→S→B. Do not turn a shared dependency into a forwarding step or arrange independent paths into a serial pipeline. Trace important paths for missing branches and invented bypasses. Abstraction may combine implementation steps, but cannot change who calls whom. If an optional path needs too many extra entities, explain it in detail or a separate view instead of leaving dangling edges.

**Frames and edges mean different things.** Frames assert named containment: distinguish responsibility, process, deployment and trust boundaries. An ordinary relationship joins the actual named source and target entities at their outlines, even across frames; do not stop at a frame or convenient blank space when a specific endpoint is known. A line entering a frame must still visibly reach its intended entity. Reserve frame-level edges for genuinely group-level relationships. Crossings are not junctions; captions cannot repair incorrect geometry or semantics.

**Use color as an index.** Assign restrained, distinct accents to meaningful entities/groups and reuse each accent with the same name in its matching detail. Group detail by that ownership, not alphabetical labels or visual order. Cross-group explanations use neutral styling or explicit named accents; do not give a mixed-topic panel one misleading group color. Keep names visible so color is not the sole identifier.

**Compose for connections.** Place connected entities on shared rows or columns when practical, then reserve space for orthogonal bends and labels. Use straight horizontal/vertical segments for ordinary component connections, with small rounded corners if desired. Reposition nodes before adding detours; do not compensate for misalignment with sweeping curves or diagonal shortcuts. An exceptional nonorthogonal path needs a clear explanatory benefit. Align comparable boxes, headings and baselines with shared guides and consistent gaps. Select an appropriate responsive grid from actual content and available width, including padding and borders; no universal column count.

**Keep geometry coupled.** Shapes, ports and paths use one coordinate system or one layout-derived source of positions. Endpoints stay on the intended entity outline after resizing or wrapping. Place each short relation label next to a clear segment of its own edge, with consistent spacing on comparable edges. Long protocol strings and explanatory sentences belong in detail; wrap or shorten labels to their reserved bounds instead of drawing unbounded SVG text. Reserve text bounds, arrowhead clearance and frame-title/legend space. Routes must avoid unrelated nodes and text; labels must not cover other labels, nodes or boundaries. A backing may interrupt its own edge only. Fix a collision by changing spacing, wording or route, never by masking another element.

**Design for the displayed scale.** Main entity names should read like normal presentation text (roughly 16–20 CSS px), with legible relation labels (roughly 13–15 CSS px) at the actual host viewport, not merely in a large SVG viewBox. Choose fewer displayed details, more space or separate related views before shrinking typography. Keep uniform text/arrowhead scaling; allow detail to scroll. The main relationships should be understandable without magnification or consulting the evidence table.

Before delivery, check semantics and geometry separately: trace the important paths and frame memberships against the facts; then check actual display scale, endpoints, alignment, clipping and every label's reserved space. Text overlap/occlusion, a wrong endpoint or a fabricated relationship fails acceptance. Keep the implementation small; use SVG, HTML/CSS or a small local helper as appropriate, without building an elaborate layout engine.
